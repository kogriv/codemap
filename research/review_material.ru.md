# Материал для обзора: подходы к анализу кода и где у каждого слепое пятно

**R1-C103.** Это **материал, а не статья**: конспект с цифрами и ссылками, из которого статью пишет автор. Каждое
число здесь взято из карточки инструмента (`tools/*.md`), из [`comparison.md`](comparison.md) или из
[`00_landscape.md`](00_landscape.md); при расхождении права карточка. Что измерено руками, а что известно только по
описаниям, помечено в каждой строке. Статус: черновик материала от 2026-11-20, пополняется.

## 0. Вопрос обзора

Не «какой инструмент лучше», а **на какой вопрос о коде отвечает каждый подход, и чего он не видит**. Агенту,
ревьюеру и новичку в проекте нужны разные ответы: найти место, понять, кто от чего зависит, узнать, что
сломается при правке, увидеть архитектуру, получить объяснение. Подходы различаются тем, какие из этих вопросов
им вообще доступны.

Пять вопросов, по которым меряли все карточки (одно дерево: 280 файлов, 207 на Python, закреплённый коммит):

| | вопрос |
|---|---|
| T1 | где определён символ |
| T2 | кто его вызывает |
| T3 | что от него зависит (радиус правки) |
| T4 | что сломается, если изменить сигнатуру (как именно вызывают) |
| T5 | архитектура: слои, циклы импорта |

Т1–T3 — **точечные** вопросы: у них есть затравка, символ. T4–T5 — вопросы о **графе целиком**: затравки нет. Это
различие оказалось главным выводом всей серии (пост 6): почти все инструменты отвечают на первые три и молчат на
последние два.

## 1. Подходы — таксономия, перерисованная под то, к чему сошлось поле

В `00_landscape.md` семейства выделены по устройству (август 2026). Поле с тех пор сошлось к одному типу —
«контекст для ИИ + граф + MCP в одном инструменте», — поэтому здесь подходы разложены по тому, **как они
получают ответ**.

| # | подход | как отвечает | представители | у нас измерено | главное слепое пятно |
|---|---|---|---|---|---|
| 1 | Текстовый поиск | совпадение строки | grep, ripgrep | как база в замерах `pack` | не знает структуры: не отличит вызов от упоминания, не видит сигнатур |
| 2 | Поиск, где каждое решение принимает модель | вопрос «да/нет» модели про каждый файл | jevgrep | ✅ [карточка](tools/jevgrep.md) | T4–T5 невыразимы; ответ не воспроизводится побайтово; код уходит к провайдеру |
| 3 | Семантический поиск по эмбеддингам | близость векторов | cocoindex-code; индексы IDE-ассистентов | ✅ cocoindex-code ([карточка](tools/cocoindex-code.md)) | структуры нет вовсе: T2–T5 неприменимы |
| 4 | Карта репозитория для контекста модели | сжатый список символов под бюджет | aider repo-map, Repomix | ✖ по описаниям | ранжирование без проверки, нужен ли выбранный контекст |
| 5 | Точные индексы кода (code intelligence) | компилятор/LSP строит индекс | LSP, SCIP/LSIF, Sourcegraph, Kythe, Glean | ◐ SCIP как формат экспорта | нужен работающий язык-сервер и окружение; индекс бинарный, не сравнивается между версиями |
| 6 | Статический граф кода для агентов (MCP) | разбор исходника в граф | codemap, CodeGraph, GitNexus, graphlens, OntoIndex, grafema, Graphify (кодовый слой) | ✅ все перечисленные | у каждого свои: см. §2 — чаще всего ленивые импорты и вопросы о графе целиком |
| 7 | Языки запросов и структурный поиск | DSL или шаблон по AST/потокам данных | CodeQL, Semgrep, ast-grep, Joern | ✖ по описаниям | мощно, но вопрос надо уметь сформулировать; не про контекст для агента |
| 8 | Архитектурные гейты | контракт слоёв проверяется в CI | import-linter (grimp), codemap check, гарантии grafema | ✅ [import-linter](tools/import-linter.md), grafema | самое слабое место — не граф, а конфигурация: опечатка проходит без проверки |
| 9 | Граф и объяснение пишет модель | субагенты пишут связи, слои, экскурсию | Understand-Anything; вики-генераторы | ✅ [карточка](tools/understand-anything.md) (детерминированный слой + пилот) | на пилоте модель не написала ни одной связи; не детерминирован по построению |
| 10 | Платформы качества и линтеры | правила и метрики по коду | SonarQube, CodeScene, PVS-Studio, radon, vulture | ✖ **не разобраны** | — (см. §4) |
| 11 | Боты ИИ-ревью | модель читает дифф | CodeRabbit, Greptile, ревью в Copilot | ✖ **не разобраны** | — (см. §4) |

## 2. Сквозные наблюдения — с цифрами

### 2.1 Одно дерево, 45 циклов импорта: кто сколько видит

Лучшая таблица для обзора: один и тот же факт о коде, разные инструменты. Эталон — 266 зависимостей модулей и
45 циклов; его независимо, без общего кода, воспроизвёл grimp (import-linter): 266 из 266 рёбер, 45 из 45 циклов.

| инструмент | циклов видно | почему | источник |
|---|---|---|---|
| grimp (import-linter) | **45 из 45** | читает импорты в любом месте | [карточка](tools/import-linter.md) |
| codemap | 45 из 45 | то же, с пометкой области (модуль / функция / TYPE_CHECKING) | эталон |
| grafema | 8 из 45 | читает все области по замыслу, но три дефекта Python-пути (с двумя исправленными — 42 из 45) | [карточка](tools/grafema.md) |
| Graphify | 2 из 45 | импорт внутри функции не даёт зависимости модуля | [карточка](tools/graphify.md) |
| Understand-Anything | **0 из 45** | читает только импорты верхнего уровня; агенту запрещено перепроверять | [карточка](tools/understand-anything.md) |
| CodeGraph 1.6.0 | сообщает 136, настоящих 41 | идёт по рёбрам вызовов, разрешённым по имени | [карточка](tools/codegraph.md), [перемер](codegraph_remeasure.md) |
| CodeGraph 1.6.2 | сообщает 25, настоящих 16 | после исправлений автора | [перемер](codegraph_remeasure.md) |

Причина почти всех потерь одна: **на этом дереве каждый цикл замыкается через импорт не на верхнем уровне
модуля** (ленивый импорт внутри функции). Граф, который такие импорты пропускает, не просто меньше — он
сообщает «циклов нет» о дереве с 45 циклами.

Оговорка: дерево одно и принадлежит автору codemap; это одна форма кода, а не выборка.

### 2.2 Точность, когда ответ есть, высокая у всех

Где инструмент отвечает, он обычно прав: точность рёбер импорта — Graphify 99.6 %, grafema 99.4 %,
Understand-Anything 99.5 %. Разница не в точности, а в **полноте** и в том, **сообщает ли инструмент о том, чего
не видит**. Отсюда сквозная тема серии: молчаливая неполнота (обрезка без пометки, отказ с кодом выхода 0,
`truncated: false`, когда из 57 вызывающих в ответе 30, — OntoIndex, пост 7).

### 2.3 Детерминизм

| побайтово тот же результат на том же входе | инструменты |
|---|---|
| да | codemap (быстрый режим), Graphify, детерминированный слой Understand-Anything, набор рёбер grafema |
| нет | граф OntoIndex, БД graphlens, ответы jevgrep (модель), граф Understand-Anything целиком (по построению) |

Для агента и CI это не мелочь: ответ, который меняется без изменения кода, нельзя сравнить между версиями.

### 2.4 Две пустые колонки

T4 (как именно вызывают функцию: позиционно, по имени, через распаковку) и T5 (слои, циклы) — пустые почти у
всех измеренных инструментов, включая 68-тысячезвёздный CodeGraph, который оказался быстрее codemap (пост 6).
Точечный вопрос начинается с символа; вопрос о графе целиком — нет, и инструменты, построенные вокруг поиска,
до него не доходят.

### 2.5 Объяснение — отдельный продукт

У Understand-Anything больше звёзд, чем почти у любого инструмента, отвечающего на T1–T5, хотя на T2–T5 он не
отвечает. Он отвечает на вопрос новичка: экскурсия, описание модулей, связь Dockerfile с кодом. **Запрос на
понимание кода есть, и большая его часть — запрос на объяснение, а не на граф.** Это вывод, который обзору стоит
сделать честно, даже если он не в пользу графовых инструментов.

## 3. Где codemap в этой карте (одним абзацем, без рекламы)

Подход 6 и 8 одновременно: граф по исходнику без импорта анализируемого кода, детерминированный, с пометкой
происхождения каждого узла (ядро / тесты / документы) и с гейтом архитектуры. Сильные стороны измерены: T4 и T5,
все области импорта, воспроизводимость. Слабые — тоже: только Python; функция контекста для агента (`pack`) в
четырёх замерах не показала пользы против `grep` (пост 14); объяснять кодовую базу он не умеет.

## 4. Чего в материале нет — сделать до обзора

- **Подходы 10 и 11** (платформы качества, боты ИИ-ревью): не разобраны даже по описаниям. Минимум для обзора —
  что каждый обещает, на каком вопросе из T1–T5 он стоит, лицензия и модель цены. По документации, с пометкой
  «не измерено».
- **Отечественные инструменты** для русскоязычного читателя: PVS-Studio (статический анализ), ассистенты кода
  Яндекса и Сбера. По документации.
- **Подходы 4, 5, 7** описаны в `00_landscape.md` по чтению (август). Обновить строки, ничего не меряя, и так и
  написать.
- **Внешние цифры о проблеме** (рост генерации кода ИИ, здоровье кодовых баз) — в материале исследования
  R1-C104, после проверки по первоисточникам.
- **Даты версий.** Каждая цифра §2 описывает версию, которую мерили; в обзоре у каждой строки должна стоять дата.

## 5. Ограничения, которые обзор должен назвать

- Все измерения — на одном Python-дереве автора codemap. Одна форма кода, не выборка.
- Эталон построен codemap; независимое подтверждение есть для графа импортов (grimp — точное совпадение) и
  для вызывающих одного класса (три реализации без общего кода: 58 / 58 / 60), не для всего.
- Автор обзора — автор одного из инструментов. Поэтому в серии публикуется и то, где codemap проигрывает
  (скорость CodeGraph, звёзды Understand-Anything, `pack` против `grep`), и дефекты, найденные в codemap
  вопросами, написанными для чужих инструментов (посты 11, 12, 13).
