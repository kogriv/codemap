## 1. Зачем ещё одна обкатка

Две прошлые обкатки были **одноосевые** и каждая нашла ровно один доминирующий гэп
(F1 — область → M6; F5 — швы диспетчеризации → M7). Обе оси теперь закрыты. Чтобы найти
**больше реальных нестыковок**, эта обкатка сознательно **перебирает архетипы вопросов**,
которые инструмент ещё не нагружал, — по одной реальной задаче bquant на каждый, с
предрегистрацией «где сломается».

### Покрытые оси (нагружали)
- **reverse-impact** — «кто использует X» → F1 (закрыт M6).
- **forward-callchain** — «что исполняется при X» → F5 (закрыт M7).

### Непокрытые оси (нагружаем здесь)
- **contract/exemplar** — «как расширить точку расширения» (T1).
- **dataflow по строковому ключу** — «проследи колонку датафрейма» (T2).
- **change-set reasoning** — «что сломает смена сигнатуры» (T3).
- **RAG-самодостаточность** — «дай чанк, достаточный для правки» (T4).
- **reachability/dead-code после M7** — регресс-проверка достижимости (T5).

## 2. Таксономия гэпов (классифицируем по причине, не симптому)

| Категория | Значение | Прецедент |
|---|---|---|
| **Extraction** | инфы нет в графе вообще | F1 |
| **Representation** | инфа есть, но не в той форме под вопрос | F3 |
| **Query-surface** | инфа есть, но спросить нечем | F2 |
| **Precision** | есть, но over/under-approximation | F5-мост |

Каждая находка ниже получает категорию — это прямо диктует форму фикса (новый экстрактор /
новый вид / новая команда / уточнение метки).

## 3. Конфигурация прогона

- **Граф:** repo-scoped, `--mode full --deep` (честная полная конфигурация: ядро + потребители
  tests/examples/research/scripts + доки). Тот же билд, что в обкатке-2 / M7.
- **Правило:** каждую задачу решаем **только через codemap** (указываем команду/вид). Где
  приходится звать grep/чтение — это и есть гэп.
- **Вывод на задачу:** вопрос потребителя → попытка (команда) → вердикт **полно / частично /
  никак** → ground-truth (grep/чтение) → категория гэпа → id находки `F6…` или «покрыто».
- Спайк-скрипты — в scratchpad, в репо не тащим. `bquest` не трогаем.

## 4. Пять задач и предрегистрированные гипотезы

### T1 — Extension: «добавь новую swing-стратегию, как ZigZag»
**Потребитель:** ИИ/разработчик реализует фичу на точке расширения.
**Что нужно из графа:** (i) контракт (методы Protocol + сигнатуры), (ii) шов регистрации,
(iii) путь конструирования/проводки, (iv) образец-реализация.
**Виды:** `query SwingStrategy`, `export rag` на существующей стратегии, `export mermaid --mkind class`.
**Гипотеза H1:** члены реестра (данные M7) в графе есть, но **нет вида «семейство/контракт»** —
из графа не собирается «эти N классов = семейство swing, обязаны реализовать `calculate_*`;
вот образец». → ожидаю подтверждение **F4** + возможный новый *representation/query-surface* гэп.

### T2 — Dataflow по строковому ключу: «проследи колонку `macd_hist` от производства до потребления»
**Потребитель:** отладка «почему метрика зоны кривая».
**Что нужно:** пройти по датафрейм-колонке (`indicator_col='macd_hist'`), не по символу.
**Виды:** — (кандидатов почти нет; попробуем `query`, `rag` текст-поиск).
**Гипотеза H2:** **extraction-гэп** — строковые колонки датафрейма невидимы графу; связь
«кто пишет `df['macd_hist']` ↔ кто читает» не выражается. Сильный кандидат в **F6 (dataflow-blindness
по строковым ключам)**.

### T3 — Change-set: «поменяй сигнатуру ходового core-fn (напр. `get_indicator_params`)»
**Потребитель:** рефактор с breaking-change.
**Что нужно:** не просто «кто ссылается», а «какие call-sites реально **сломаются**»
(позиционные аргументы / kwargs / арность).
**Виды:** `report impact --symbol`, `query`.
**Гипотеза H3:** `impact` — на уровне **ссылок**, а не арности/аргументов вызова; для рефактора
он даёт список-кандидат, но не отличает ломкий call-site от безобидного упоминания. →
*precision/representation* гэп, кандидат **F7 (call-site без арг-контракта)**.

### T4 — RAG-самодостаточность: «дай достаточно, чтобы модифицировать `MACDZoneAnalyzer`»
**Потребитель:** ИИ-редактор, собирающий контекст под правку.
**Что нужно:** самодостаточный чанк — что класс делает, что вызывает, куда делегирует
(deprecated → делегирует в pipeline), кто его зовёт.
**Виды:** `export rag` (чанк класса).
**Гипотеза H4:** **F3 подтверждён** — класс-чанк не агрегирует call-соседей своих методов;
шов делегирования (метод → `analyze_zones`) виден на ребре метода, но не в чанке класса. →
*representation* гэп.

### T5 — Reachability/dead-code после M7 (регресс)
**Потребитель:** аудит «что мёртвое / все ли точки входа достижимы».
**Что нужно:** `report dead-code`, сверка с реальностью.
**Виды:** `report dead-code`.
**Гипотеза H5:** взаимодействие мост-рёбер M7 с dead-code не проверено. Либо (a) registry-
impl'ы теперь корректно достижимы через мост (регресс OK), либо (b) dead-code даёт
false-positive на плагинах (зарегистрированы, но зовутся только динамически) / наоборот
false-negative. Кандидат **F8**.

## 5. Результаты прогона

**Граф:** repo-scoped `full --deep`, схема 0.5 — 3210 узлов (205 mod / 285 cls / 2042 fn /
631 attr / 47 doc), 7542 ребра (calls 2385 / contains 3047 / references 782 / imports 632 /
export 479 / decorated_by 165 / inherits 52). Сборка ~56с. Тот же билд для всех пяти задач.

### T1 — Extension (contract/exemplar) → **F4 подтверждён и расширен** · Query-surface
Гипотеза H1 **подтвердилась**. Данные семейства **полностью в графе**:
- 12 узлов с `extras.registry` (`{decorator: …register_swing_strategy, key: 'zigzag'}`, …);
- Protocol `SwingCalculationStrategy` несёт контракт-методы через `contains`
  (`calculate`, `calculate_global`, `aggregate_for_zone`, `get_metadata`, `config_hash`);
- RAG-текст ZigZag прямо пишет «Registered as 'zigzag'».

Но **вид семейства не собирается ниоткуда**:
- `query SwingCalculationStrategy` → `subclasses: —` (0 связей с 4 реализациями — структурная
  типизация, Protocol не наследуется);
- `query ZigZagSwingStrategy` → `bases: —` (с конца реализации семейство/контракт не виден);
- `export mermaid --mkind class --scope …swing` → **пустой** classDiagram (строится только по
  `inherits`, а их у семейства нет).

**Итог:** ИИ, которому сказали «добавь swing-стратегию как ZigZag», из codemap не получит ни
контракта, ни соседей-реализаций, ни декоратора регистрации — **при том что всё это в графе** —
и уйдёт в grep. Это **F4** (registry-map/family view), эмпирически подтверждён и **расширен с
диаграммы на всю query-поверхность**. Фикс: синтезировать `implements`-рёбра Protocol↔члены-семейства
(по таблице реестра) + вид/диаграмма семейства + образец.

### T2 — Dataflow по строковому ключу `macd_hist` → **F6 (новый)** · Extraction
Гипотеза H2 **подтвердилась жёстко**. `macd_hist` — датафрейм-колонка (grep: 47 употреблений;
производитель `indicators/custom/macd.py`, потребители `visualization/*`, `data/schemas.py`,
`indicator_col='macd_hist'` в pipeline). В графе:
- `query macd_hist` → `defined at: —`;
- **ноль** узлов/рёбер/extras-ключей содержат `macd_hist`; нет ни одного extras про колонки;
- RAG-текст-фолбэк — **0 попаданий** (чанки из докстрингов/сигнатур, не из строковых литералов
  тела) → здесь codemap **хуже grep**.

**Итог: F6 — dataflow-слепота по строковым ключам** (dataframe-колонки, config-ключи как
данные). Весь аналитический pipeline bquant прошивает данные через строковые колонки — граф не
видит ни одной. Это эмпирическое подтверждение отложенного CM-10 (value-level data-flow, §7):
теперь это felt gap, не теоретический. Категория **Extraction** (нужен новый лёгкий проход:
литералы-подписки `df['col']` / kwargs `indicator_col=` → `column`-узлы + `writes`/`reads`-рёбра).

### T3 — Change-set (смена сигнатуры `get_indicator_params`) → **F7 (новый)** · Representation+Precision
Гипотеза H3 **подтвердилась**. `get_indicator_params(indicator, **overrides)`, 5 call-sites (grep),
все — один позиционный строковый аргумент. `report impact` даёт 4 references по роутам
(вызывающие **функции**), но:
- рёбра `calls` несут в extras **только `resolution`** — ноль про арность/kwargs/позиционность
  → нельзя ответить «какие call-sites сломает keyword-only / новый обязательный аргумент»;
- call-sites **схлопнуты до объемлющей функции**: `examples/01` зовёт дважды (rsi+macd) →
  в impact «examples (1)» → рефактор **недосчитает** места.

**Итог: F7 — call-граф функционально-гранулярен и без арг-контракта.** Для архетипа «change-set
reasoning» (одна из самых частых реальных задач рефактора) codemap недоотвечает — и это **не**
потолок резолва (рёбра разрешены), а выбор модели. Категория **Representation** (ребро
function→function вместо call-site) + **Precision** (нет арг-контракта). Фикс: call-site-узлы/метки
с `argcount`/`kwnames`; либо хотя бы счётчик вызовов на ребре + захват имён kwargs.

### T4 — RAG-самодостаточность (`MACDZoneAnalyzer`) → **F3 подтверждён** · Representation
Гипотеза H4 **подтвердилась точно**. Function-чанки несут богатые `neighbors.calls`
(`extract_zone_features` → все compute-методы стратегий через мост M7). Но:
- **класс-чанк** несёт максимум `bases`/`subclasses`, и то лишь 69/285 классов; у `MACDZoneAnalyzer`
  **вообще нет `neighbors`** (ни базы, ни подклассов → пусто);
- при этом её **метод-чанк** `analyze_complete_modular` содержит ключевейший факт —
  делегирование в `analyze_zones` / `detect_zones` / `with_indicator` / `build` (шов deprecated→pipeline).

**Итог:** ИИ, вытянувший класс-чанк «как модифицировать `MACDZoneAnalyzer`», получает
«Deprecated wrapper» + место и **не узнаёт, что класс делегирует в pipeline** — факт в одном хопе,
но застрял на метод-чанке, который ретривер может не со-локировать. **F3** подтверждён.
Категория **Representation**. Фикс: класс-чанк агрегирует union call-соседей своих методов
(с меткой «via <метод>»). Красиво стыкуется с M7 — мост уже положил нужные рёбра на методы.

### T5 — Reachability / dead-code после M7 → H5(M7) **опровергнута** (чисто); **F8 (новый)** на оси M6 · Representation
Гипотеза H5 про M7 **опровергнута — и это хорошо:** registry-стратегии, достижимые только через
мост, корректно **живые** (ZigZag: 52 входящих calls к членам — 9 registry-candidate + 13 deep +
30 imported; аналогично FindPeaks, ZeroCrossingDetection). Мост M7 **не** ломает dead-code — регресса нет.

Но проверка достижимости вскрыла гэп на **соседней оси (M6)**: `report dead-code` даёт
**124 orphan-модуля**, из них по роутам — core 8 / examples 11 / research 24 / scripts 6 /
**tests 75**. То есть **116/124 (94%) — consumer-entrypoint'ы, orphan по природе** (тесты/примеры/
скрипты никто не импортирует). Осмысленных (core) — 8, и те в основном пакет-`__init__`/CLI/данные
(`bquant.core`, `bquant.cli`, `bquant.data.samples.embedded.*`).

**Итог: F8 — `report dead-code` не провенанс-осознан.** Отчёт спроектирован под один пакет; после
M6 (мульти-рут) он тонет в consumer-entrypoint'ах. Категория **Representation/Query-surface**. Фикс:
ограничить orphan-анализ роутом `core` (или исключать consumer-роуты/точки входа), либо
группировать по роуту с дисклеймером — как это уже делает `report impact`.

### Итог реализации (2026-07-29, вехи M8–M12)
Все пять находок реализованы в тот же день, в порядке «дёшево×ценно» (F8→F4→F3→F7→F6). Схема
`0.5 → 0.8` (M9 `implements`, M11 арг-контракт на `calls`, M12 `column`/`reads`/`writes`). Тесты
57 (до) → **83** (+26; фикстуры dispatchpkg/base, argpkg, flowpkg). Детерминизм в каждой вехе.
Три из пяти (F4/F7/частично F3) не требовали нового тяжёлого анализа — данные были в графе,
не хватало формы/связи/поверхности; F6 — единственный новый экстрактор (по колонкам, не по значениям).
