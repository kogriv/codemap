# Гэп: `build` выполняет скомпилированные модули анализируемого дерева

**Дата:** 2026-11-10. **Источник:** разбор падений сборки в замере R1-C93 (RepoBench), репозиторий с
вендоренным `charset_normalizer` и его `md.cp38-win32.pyd`. **Статус:** ✅ закрыто 2026-11-10 (0.0.37); дизайн —
[`docs/design/build_on_foreign_trees.md`](../docs/design/build_on_foreign_trees.md), бэклог R1-C96.

## 1. Что показали

README обещает: «source-only (static `ast`/`griffe`, **never imports the target**)». Обещание не выполняется.

codemap вызывает `griffe.load(...)`, не передавая `allow_inspection`. По умолчанию griffe его включает: модуль, у
которого нет исходника (`.so`, `.pyd`, `.pyc` рядом с пакетом, а не в `__pycache__`), griffe не может прочитать,
поэтому **импортирует** его и инспектирует живой объект. Импорт расширения выполняет его код инициализации,
импорт `.pyc` выполняет тело модуля.

Воспроизведение, пакет из двух файлов:
- `pkg/__init__.py` пустой;
- `pkg/evil.pyc`, скомпилированный из модуля, который при импорте пишет файл-маркер (исходник удалён).

`codemap build pkg` создаёт маркер, затем падает с `'utf-8' codec can't decode byte …`: поведенческий слой
читает `.pyc` как текст. С `.so`, собранным из пяти строк C (`PyInit_fast` пишет маркер), картина та же. Маркер
появляется и в быстром тире, и в `--deep`.

**Сколько это длится.** Проверено на опубликованных версиях под Python 3.12: 0.0.10, 0.0.20 и 0.0.36 создают
маркер. `.pyc` грузится только под той версией Python, которой собран, а `.so` только под своей платформой.
Поэтому под 3.14 та же проба давала «none»: файл не загрузился, но инспекция всё равно была включена.

**Второй вход того же рода.** Если griffe не находит модуль на диске и инспекция включена, он импортирует
верхний модуль по имени (`dynamic_import`). Для `build <каталог>` это редкий путь, но тот же класс.

## 2. Почему так

Умолчание griffe рассчитано на генератор документации, которому живой объект полезен. codemap — статический
анализатор, и умолчание никто не переопределил. Ни один тест не клал в дерево скомпилированный модуль.

## 3. Чем это опасно

`codemap build` (и всё, что строит граф: `serve --watch`, post-commit-хук, `refresh`, `review` со сборкой) на
чужом дереве с подложенным `.pyc` или `.so` — это выполнение чужого кода с правами пользователя. Пользователь не
ждёт этого, потому что README прямо обещает обратное. Вендоренные `site-packages` и `venv/` внутри репозитория —
обычное дело (в R1-C93 таких деревьев несколько), так что скомпилированный модуль в дереве — не экзотика.

## 4. Что считать исправлением

- `build` не импортирует ничего из анализируемого дерева ни в одном тире: проба с маркером (`.pyc` и `.so`)
  маркер не создаёт.
- Модуль без исходника не роняет сборку и не исчезает молча: он перечислен как не загруженный.
- Модуль, у которого рядом лежит и исходник, и скомпилированная копия (`md.py` + `md.cp38-win32.pyd`), строится
  из исходника на любой файловой системе. Сейчас griffe выбирает файл по порядку обхода каталога, и на машине
  с другим порядком побеждал `.pyd`.
