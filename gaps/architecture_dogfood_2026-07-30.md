**Дата:** 2026-07-30

**последняя ось нового класса ценности** перед развилкой «пользоваться/выносить».

## 1. Зачем эта ось

Все прошлые оси — **локальные** (символ, дифф, колонка). Архитектор задаёт **глобальный** вопрос: форма
системы. Что уже есть: `report dependencies` = import-циклы + самые-импортируемые модули. Это **узкий
срез** (один вид связности). Не покрыто: **слои** и направление зависимостей между ними (нарушения),
**coupling/instability** (Ca/Ce/I по модулю), **god-объекты/хотспоты** (класс с раздутым числом методов +
высокий fan-in; хаб в call-графе), **синтез** всего в один «architecture overview». Данные для всего этого
уже в графе (import-граф, calls, contains, провенанс) — вопрос **поверхности и агрегации**.

## 2. Метод и таксономия

Ведём вопросы архитектора через `serve`/`report`. На каждый: намерение → op/report → что вернулось →
хватило ли → категория гэпа (Extraction/Representation/Query-surface/Precision/Workflow/Soundness).
**Честность:** метрики считаем на **core**-пакете (провенанс `core`), consumer-руты (tests/examples) не
мешаем в архитектуру ядра. Пороги god-объектов/хотспотов — по распределению, не magic-числа.

## 3. Конфигурация прогона

- **Граф:** repo-scoped `full --deep`, схема 0.9 — 4217 узлов / 9935 рёбер (`b1_graph_v09`).
- **Есть:** `import_graph` (модуль→модуль), `import_cycles`, `_calls` (символьный call-граф), `contains`
  (класс→методы), провенанс `root`. **Нет** (гипотеза): слоёв, coupling-метрик, hotspot-детекции, синтеза.
- **Инструмент:** `Session.handle` + `report dependencies`.

## 4. Вопросы архитектора и гипотезы (предрегистрация)

### G1 — «Какие слои и как они зависят? Есть ли нарушения направления?»
Пакет заявляет слои (core → data → indicators → analysis → visualization). Архитектор хочет **матрицу
межслойных зависимостей** и **нарушения** (нижний слой импортирует верхний / цикл между слоями).
*Гипотеза H-A9a:* **нет** слоевого вида. `dependencies` даёт per-module циклы и top-imported, но не
агрегирует модули в слои и не проверяет направление. Данные (import-рёбра + пути модулей) есть. →
кандидат **F18** (Query-surface/Workflow: нет слоёв/нарушений).

### G2 — «Насколько связаны модули? Где нестабильные хабы?»
Ca (кто зависит от меня), Ce (от кого завишу я), Instability I=Ce/(Ca+Ce). Классика для «что трогать
опасно» (стабильное ядро) vs «что легко менять».
*Гипотеза H-A9b:* **нет** coupling-метрик — только сырое in-degree в тексте отчёта. → кандидат **F19**
(Query-surface: нет Ca/Ce/instability).

### G3 — «Где god-объекты / хотспоты?»
Класс с раздутым числом методов + высокий fan-in; функция-хаб (высокий in+out в call-графе). Точки
концентрации риска/сложности.
*Гипотеза H-A9c:* **нет** hotspot-детекции — большой класс (напр. `ZoneAnalysisPipeline`/`MACDZoneAnalyzer`)
или call-хаб нигде не выделен. Данные (contains-размер, call-степени) есть. → кандидат **F20**
(Query-surface: нет god-объектов/хотспотов).

### G4 — «Дай форму системы одним видом»
Синтез: циклы + слои + coupling + хотспоты в один `report architecture`.
*Гипотеза H-A9d:* **нет** синтез-отчёта. Складывается дёшево поверх G1–G3. → **F21** (Workflow: нет
architecture overview) — вбирает G1–G3 в одну веху.

**Ожидание по итогу:** одна веха **M16** = `report architecture` + Query-методы `layers()`/`coupling()`/
`hotspots()`; **без схемы** (всё поверх готовых рёбер/провенанса), как M13/M15.

## 5. Прогон

**Граф:** repo-scoped `full --deep`, схема 0.9. Core: **89 модулей / 632 import-ребра / 1 цикл**.
Отчёты сейчас: `api-surface | behavior | dead-code | dependencies` — **глобального вида системы нет**.

### G1 — слои и направление → **F18 (Query-surface/Workflow)**
Op нет. Вручную из import-графа: **8 слоёв** (analysis, core, data, indicators, visualization, cli, ml,
root). Межслойные рёбра (core-only): `analysis→core 38`, `indicators→core 24`, `data→core 13`,
`visualization→core 8`, `analysis→indicators 3`. Картина **чистая** (всё сходится в `core`, ядро —
сток; обратных `core→верх` нет). Но ответ архитектор получает **только руками** — ни матрицы, ни
проверки нарушений. Честная проверка нарушений **без хардкода порядка**: слоевая пара с рёбрами в
**обе** стороны (взаимозависимость) = smell. → **F18**.

### G2 — coupling / instability → **F19 (Query-surface)**
Метода нет. Вручную Ca/Ce/I: `core.logging_config` **Ca=94, I=0.01** (максимально стабильный лист —
верно, его все зовут), `core.exceptions` **Ca=31, I=0.00** (стабильное ядро), `analysis.zones`
**Ca=33 Ce=9 I=0.21**, `indicators` **Ca=24 Ce=6 I=0.20**. Ровно то, что нужно для «что трогать опасно»
(стабильное) vs «что легко» (нестабильное). В отчёте — только сырое in-degree. → **F19**.

### G3 — god-объекты / хотспоты → **F20 (Query-surface)**
Детекции нет. Вручную топ-классы по числу методов: `ZoneVisualizer` **35**, `NotebookSimulator` 23,
`StatisticalPlots` 23, `ZoneAnalysisPipeline` **20**, `StrategyRegistry` 17 — реальные god-object-кандидаты.
Call-хабы (in+out): `ContextualLogger.info` 105, `get_sample_data` 83, `MACDZoneAnalyzer` 57 — полезно,
но **логгер доминирует** → отчёт обязан помечать pervasive-утилиты (логгер) как ожидаемый шум, а не риск.
→ **F20**.

### G4 — синтез одним видом → **F21 (Workflow)**
`report architecture` нет — отчёты локальны. Синтез G1–G3 (+ переиспользовать циклы) складывается дёшево.
→ **F21**, вбирает G1–G3 в одну веху.
