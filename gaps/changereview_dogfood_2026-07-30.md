# codemap — обкатка A11: diff / change-review (PR-дифф → что ревьюить)

**Дата:** 2026-07-30
**Ось:** A11 (Consumer-task) из реестра `dogfood_axes.md` — следующая по приоритету после B1.
**Тип:** обкатка на реальном артефакте — ревьюер получает **git-дифф** (изменённые файлы + диапазоны
строк) и должен через codemap ответить: *какие символы задеты, каков blast radius, что перепроверить,
что рискованно*. Ведём **только** через `serve`-ops (+`Read` исходника по `file:line`); где приходится
руками переводить хунк в имя символа или вручную сшивать N ответов — это гэп сцепки.
**Связано:** M6 impact (`gaps/observability_dogfood_2026-07-28.md`), M11 arg-contract
(`deep_dogfood_2026-07-29.md` F7), M13 serve-эргономика, `../DESIGN.md` §7.

> **Статус:** §1–§4 (мотивация, метод, гипотезы) — **ДО** прогона (falsifiable). §5–§6 — по прогону.

---

## 1. Зачем эта ось

Все прошлые обкатки начинались с **имени символа** («расскажи про X», «кто зовёт X»). Но реальный
ревью начинается не с имени, а с **диффа**: файл + диапазоны строк. Между «дифф» и «символ» —
разрыв: codemap ключует всё по id/имени, а ревьюер держит `zigzag.py @@ -63,7 +63,19 @@`. Это
**самый практичный** сценарий (ревью PR ежедневно), стоит на уже готовом impact + arg-contract +
columns_of + references — проверяем, **сцепляются ли** они во «вход ревьюера».

**Артефакт прогона.** Реальный дифф bquant `bd27eb5` (feat: populate confirmation_index) — 3 файла:
`pipeline.py`, `strategies/swing/find_peaks.py`, `strategies/swing/pivot_points.py`, хунки в
конкретных диапазонах строк. Плюс фокусный `c418409` (fix: ZigZag degrades gracefully),
`zigzag.py @@ -63`.

## 2. Метод и таксономия

Ведём задачи ревьюера **строго через serve**. На каждый шаг: намерение → op → что вернулось → хватило
ли для следующего (да/частично/тупик) → категория гэпа. Категории — прежние (Extraction /
Representation / Query-surface / Precision / Workflow / Soundness).

**Честность:** диапазоны строк диффа должны соответствовать **тому же дереву**, что в графе (иначе
номера «плывут»). Граф собран на текущем дереве (HEAD); хунки берём из **текущих** спанов реально
изменённых символов, чтобы номера строк совпадали с узлами — операционный инвариант, который сам по
себе часть находки.

## 3. Конфигурация прогона

- **Граф:** repo-scoped `full --deep`, схема 0.9 — 4217 узлов / 9935 рёбер (уже построен, `b1_graph_v09`).
- **Данные для A11 (проверено):** core-функции (863) несут `file` (`bquant/…py`, совпадает с diff-путём)
  + `lineno`/`endlineno`; **consumer-руты (tests/examples/research/scripts) `file` НЕ несут** — узел есть,
  локации файла нет.
- **Инструмент:** `Session.handle` (18 ops) + `Read` исходника.

## 4. Задачи ревьюера и гипотезы (предрегистрация)

### R1 — «Дифф на руках: какие символы изменены?» (диапазон строк → символ)
Дифф даёт `pivot_points.py`, изменены строки ~95–113 и ~399–416. Первый вопрос ревьюера — **что это за
символы**.
*Гипотеза H-A11a:* **нет op** `(file, line)`/`(file, range)` → содержащий символ. Узлы несут
`file`+`lineno`+`endlineno` (данные для containment есть), но `search` матчит только подстроку id, не
локацию. Ревьюер **вынужден руками** открыть файл и сопоставить хунк с именем **до** любого impact-запроса.
→ кандидат **F16** (Query-surface: нет резолвера локация→символ).

### R2 — «Собери ревью-досье по всему change-set» (N символов → один консолидированный вид)
Изменены ~5 символов в 3 файлах. Ревьюеру нужен **один** свод: объединённый blast radius, у кого меняется
сигнатура (call-contract), какие колонки задеты, какие тесты перепроверить, кто за пределами пакета зовёт.
*Гипотеза H-A11b:* куски есть (`impact`, `call_contract`, `columns_of`, `references`/`used_by`), но **нет
op**, принимающего **набор** символов/хунков и отдающего сшитое досье. Ревьюер делает N×M вызовов и
склеивает вручную. → кандидат **F17** (Workflow: нет change-set агрегации ревью).

### R3 — «Что перепроверить в первую очередь?» (риск/приоритет)
Даже с blast radius нет сигнала **приоритета**: изменённая функция, зовомая из многих рутов и с
разнородным call-contract = высокий риск; приватный лист = низкий.
*Гипотеза H-A11c:* сигналы есть (fan-out, число рутов-потребителей, вариативность контракта, смена
сигнатуры), но **не синтезированы** в «ревьюить первым». Возможно, переусложнение для v1 — держим как
**мягкую** гипотезу: если синтез дёшев поверх R2-досье — делаем; иначе фиксируем как осознанную границу.
→ кандидат **F18** (Workflow: нет риск-ранжирования) — по итогам R2.

### R4 — «Дифф добавляет/удаляет символы» (граница двух-графового diff)
Дифф `bd27eb5` **добавляет** методы (`confirmation_index`-логика) — их **нет** в графе, собранном на
дереве. Один граф не рассуждает про added/deleted без rebuild+compare двух графов.
*Гипотеза H-A11d:* added/deleted символы — **вне** одно-графового анализа; честная **граница v1**
(двух-графовый diff — отдельная возможность, как SQLite/watcher). Проверяю, что инструмент это **не
скрывает** (не делает вид, что новый символ существует). → скорее **boundary-запись**, чем гэп.

## 5. Прогон

**Граф:** repo-scoped `full --deep`, схема 0.9. Артефакт — реальный дифф `bd27eb5` (3 файла), хунки
сопоставлены с **текущим** деревом по containment (`file` + `[lineno,endlineno]`).

### R1 — диапазон строк → символ → **F16 (Query-surface)**
- Ни один из 18 ops не принимает `(file, line)`. `search('pivot_points')` → 36 хитов по подстроке id,
  **никак не привязанных к изменённой строке**. Ревьюер с хунком `pivot_points.py @@ +399,18` не может
  спросить «что это за символ» — только вручную открыть файл.
- **Данные для containment есть:** ручной проход `pivot_points.py:405` → внутренний
  `PivotPointsSwingStrategy._confirmation_index` [399–415] (объемлющий класс [24–488]). Узлы несут
  `file`+`lineno`+`endlineno`; не хватает **только query-поверхности**. → **F16**.

### R2 — change-set → досье → **F17 (Workflow)**
- Хунки 3 файлов → **4 различных символа** (`FindPeaks/PivotPoints.calculate_global` и `._confirmation_index`).
- **`pipeline.py:51` не разрешился ни во что** — это модульный `_SWING_CLASS_TO_NAME = {…}` (код между
  def'ами, не внутри функции). Резолвер обязан **откатываться к модулю**, иначе изменения на уровне модуля
  «проваливаются». (под-находка F16.)
- Досье потребовало **20 ручных вызовов** (4 символа × ~5 ops: impact/callers/call_contract/columns_of/query)
  + ручная склейка. **Нет** op, принимающего change-set и отдающего сшитый вид. → **F17**.

### R3 — приоритет ревью → складывается в F17 (не отдельный гэп)
- Сигналы риска **все присутствуют** после R2: fan-out вызовов, число рутов-потребителей (cross-root из
  `used_by`), число call-contract-сайтов (риск смены сигнатуры), пишет/читает ли колонки. Синтез
  «ревьюить первым» **дёшев поверх** change-set-досье (сортировка по этим полям). → реализуем как поле
  `risk` внутри F17, **не** отдельная веха. (H-A11c: синтез дёшев → делаем.)

### R4 — added/deleted → **осознанная граница v1** (не гэп)
- Дифф `bd27eb5` **добавляет** `_confirmation_index` — в графе на дереве added-символа нет; `symbol_at`
  корректно вернёт **объемлющий класс** (ревьюер увидит «новый код внутри `PivotPointsSwingStrategy`»),
  инструмент added-символ **не выдумывает**. Полноценные added/deleted требуют **двух-графового diff**
  (rebuild@base vs @head) — отдельная возможность, отложена вместе с M3.3 (watcher/SQLite). Резолвер
  **честно деградирует** до объемлющего узла. → boundary-запись, не F.

## 6. Findings

| ID | Задача | Категория | Статус | Суть | Форма фикса |
|----|--------|-----------|--------|------|-------------|
| **F16** | R1 | Query-surface | ⬜→ **M15** | нет резолвера `(file, line/range)` → символ; данные containment (`file`+`lineno`+`endlineno`) есть, поверхности нет | `Query.symbol_at(file,line)` + `symbols_in_range(file,s,e)` (внутренний-первым, **fallback к модулю**); serve op `locate` |
| **F17** | R2/R3 | Workflow | ⬜→ **M15** | нет агрегации ревью change-set: 4 символа = 20 ручных вызовов + склейка; риск не синтезирован | serve op `review`(hunks/symbols) → сшитое досье (per-symbol callers/contract/columns/cross-root + union blast + **risk-ранг**); `render_review` markdown; CLI `codemap review <diff>` (парсер unified-хунков) |

**Границы (не гэпы):** added/deleted символы (R4) — двух-графовый diff, отложено с M3.3; consumer-руты
(tests/examples) `file` не несут → дифф по тесту не локализуется (core-ревью — 80% случая; запись в бэклог).

**Гипотезы:** H-A11a → **F16** ✅; H-A11b → **F17** ✅; H-A11c → синтез риска дёшев, **вложен в F17**;
H-A11d → **граница v1** (резолвер деградирует честно). Обе находки — **query/serve-слой, без схемы**
(как M13): containment поверх готовых `lineno/endlineno`, review — агрегация готовых рёбер.

**Приоритизация:** F16 первым (фундамент — без него нет входа ревьюера), затем F17 (стоит на F16 +
готовых impact/contract/columns). Одна веха **M15**.

---

*Обкатка A11 (diff/change-review): ревьюерский вход «дифф → что ревьюить» упирается в два разрыва —
**нет локация→символ** (F16, хотя данные есть) и **нет сшивки change-set** (F17, куски есть). Оба в
query/serve-слое, без схемы. Риск-ранжирование складывается бесплатно поверх досье; added/deleted —
честная граница v1 (двух-графовый diff).*
