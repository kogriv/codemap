## 1. Краткое заключение

Ответ разработчика содержателен и в значительной части убедителен. Исправления не ограничены изменением формулировок: добавлены проверки доверительных границ, обработка некорректных JSON-запросов, синхронизация `Session`, валидация формата графа, атомарная запись файлов, учёт ролей входных файлов, корректное правило поглощения циклов, ужесточение release/security CI. В репозитории имеются отдельные исправляющие коммиты и регрессионные тесты. Проект зарегистрировал security advisory по devkit.

**Важнейшая поправка к исходному аудиту:** вывод F-12 о выпуске непроверенного `0.0.44` был фактически неверным. Красный CI был у промежуточного коммита `39c86a0`, но аннотированный тег `v0.0.44` указывает на исправленный `cd1e416`; его CI завершился `success`. Этот вывод исходного аудита следует официально отозвать. Аналогично `v0.0.46` указывает на `32a7a64`, для которого подтверждён зелёный CI.

**Главное ограничение заявления о полном закрытии аудита:** повторное чтение релизного кода обнаружило три ранее неохваченных сценария:

1. **FU-01 / F-01, P1 (предварительно):** обход проверки исполняемого `pin` через отслеживаемую Git символическую ссылку на внешний исполняемый файл. Это потенциально восстанавливает сценарий исполнения команды, закрепляемой в post-commit hook.
2. **FU-02 / F-06, P2:** рецепт `refresh` с повторяющимися `-o` или `--out` проходит проверку по первому выходному пути, но `argparse` при исполнении использует последний. Обещанная гарантия записи *в тот же граф* нарушается.
3. **FU-03 / F-11, P2/P3:** два параллельных `advise.refresh.publish_pair()` могут удалить актуальные поколения друг друга. Атомарная запись указателя `current` не равна безопасной конкурентной публикации и сборке мусора.

**Рекомендуемое действие:** принять содержательную часть ответа на первый аудит и закрыть исходные подтверждённые дефекты с оговорками, но завести FU-01…FU-03 отдельно. FU-01 проверить и устранить в первую очередь; FU-02 закрыть локальным регрессионным тестом; FU-03 оценить с учётом реального режима конкурентного обновления кэша.

## 3. Подтверждённая ошибка первоначального аудита: F-12

### 3.1. Какова была исходная претензия

В первом аудите был обнаружен коммит версии `0.0.44`, на котором матрица `tests` падала после проверки точности определений символов в self-measurement. Затем был обнаружен исправляющий коммит `cd1e416`, но на момент первоначального ответа его CI ещё не имел подтверждённого финального статуса. На основании неполной картины прозвучала претензия к релизной дисциплине, в сильной интерпретации — к публикации пакета без зелёного CI.

Это смешивало две разные вещи: состояние **промежуточного релизного коммита** и состояние **фактически опубликованной версии**.

### 3.2. Что установлено при повторной проверке

1. CI для `cd1e416cd72ad5faf26ddfa69d9c3d721f167bf6`: `status=completed`, `conclusion=success`, запуск [45113785897](https://github.com/kogriv/codemap/actions/runs/45113785897).
2. Аннотированный Git-тег [`v0.0.44`](https://github.com/kogriv/codemap/releases/tag/v0.0.44) указывает на **тот же коммит** `cd1e416`.
3. Релизная запись проекта сообщает о публикации именно этой сборки в PyPI и о сверке поведения из чистых окружений. Самостоятельное скачивание и сравнение PyPI-артефакта в рамках этого документа не производилось.
4. Для `0.0.46` проверены тег `v0.0.46` → `32a7a64677c4409d7d560dac2b1b218ffebaf919` и [CI 45124790683](https://github.com/kogriv/codemap/actions/runs/45124790683) → `success`.

### 3.3. Пересмотренный вердикт

**F-12 в части обвинения опубликованной версии в красном CI — отозвать как ошибочную.**

Остаётся лишь менее сильное замечание о читаемости хронологии: до получения зелёного CI в основную ветку был отправлен коммит с повышенной версией и сообщением, похожим на релиз. Это потенциально затрудняет интерпретацию истории со стороны, но само по себе не свидетельствует о выпуске дефектного артефакта. Не следует выдавать это за P1/P2 дефект или невыполнение релизного правила.

### 3.4. Как следовало формулировать первоначально

> «На коммите `39c86a0` поднята версия 0.0.44 и CI падает. Последующий `cd1e416` исправляет тест, но на момент проверки результат CI и фактический опубликованный артефакт ещё не подтверждены. Требуется сверить релизный тег, CI релизного коммита и PyPI перед выводом о качестве публикации».

Это исправление методики самого аудитора, а не уступка в вопросах безопасности.

## 4. Дополнительная находка FU-01: доверенная символическая ссылка как обход `pin_problem`

**Связь с исходным аудитом:** F-01 и частично F-09.  
**Подсистема:** Devkit / MCP pin / post-commit hook.  
**Предварительная критичность:** **P1**, если проектная `.mcp.json` контролируется недоверенным участником или попадает в чужой checkout.  
**Доказательность:** логический путь подтверждён чтением исходников `0.0.46`; поведение `pathlib` и Git подтверждено отдельно; эксплуатационный тест полного Devkit не проводился.  
**Риск:** непроверенный исполняемый файл может быть принят как «установленный codemap» и затем закреплён в локальном хуке.

### 4.1. Контекст исправления

Исправление R1-C121 отказывается исполнять произвольные формы из `.mcp.json` и принимает только:

- абсолютный путь к исполняемому файлу с basename `codemap` / `codemap.exe`;
- абсолютный путь к Python с аргументами `-I -m codemap`.

Дополнительно выполняется `git ls-files`, чтобы исключить исполняемый файл, который сам входит в репозиторий. Это улучшение относительно `0.0.45`, однако проблема в том, **какой путь подставляется в проверку принадлежности Git**.

### 4.2. Точный участок кода

[`codemap/devkit/install.py` на `32a7a64`, `_tracked` и `pin_problem`, строки 66–106](https://github.com/kogriv/codemap/blob/32a7a64/codemap/devkit/install.py#L66-L106):

```python
def _tracked(root: Path, path: Path) -> bool:
    try:
        rel = path.resolve().relative_to(root.resolve())
    except ValueError:
        return False
    r = subprocess.run(
        ["git", "-C", str(root), "ls-files", "--error-unmatch", "--", str(rel)],
        capture_output=True,
    )
    return r.returncode == 0
```

Далее `pin_problem()` проверяет синтаксис `pin`, basename исполняемого файла, `exe.is_file()` и результат `_tracked(root, exe)`.

Проверка имени проводится для **исходного** `Path`, а `git ls-files` — для **разрешённого** `Path` после прохождения символических ссылок. При ссылке из репозитория наружу разрешённый путь больше не находится под `root`; `_tracked()` возвращает `False`, ошибочно интерпретируя его как «не отслеживаемый Git объект».

### 4.3. Контрпример

Пусть в Git-репозитории есть индексированная символическая ссылка:

```text
project/
  tools/
    codemap  ->  /bin/bash     # Git хранит symlink
  build                     # локальный/подконтрольный проекту файл
```

В `.mcp.json` указан абсолютный путь `/path/to/project/tools/codemap` как команда MCP-сервера. Он указывает на реальный Bash, но называется `codemap`.

При проверке:

| Условие `pin_problem()` | Результат |
|---|---|
| `pin[0]` — абсолютный путь | Выполнено |
| `exe.name == "codemap"` | Выполнено |
| `exe.is_file()` | Выполнено: symlink ведёт на существующий исполняемый файл |
| `path.resolve().relative_to(root)` внутри `_tracked()` | `ValueError`: разрешён `/usr/bin/bash` или `/bin/bash` вне корня |
| `_tracked(root, exe)` | `False`, хотя **сам symlink** индексирован Git |
| `pin_problem()` | Возвращает `None` — путь допускается |

Уже существующий механизм `status`/`update` может работать с таким `pin`; при штатном `update` он может попасть в шаблон локального хука. Шаблон содержит:

```bash
C={{pin_assign}}
# ...
cd "$ROOT"
nice -n 19 $C build {{package_sh}} --deep --repeat 2 ...
```

[Источник шаблона на релизном коммите](https://github.com/kogriv/codemap/blob/32a7a64/codemap/devkit/templates/post-commit.sh#L8-L28).

Если `$C` в результате указывает на Bash, первым аргументом оказывается `build`. Для Bash это имя shell-скрипта в текущем каталоге. Получается правдоподобный сценарий выполнения подготовленного проектного файла во время post-commit. Для утверждения о фактической эксплуатации требуется end-to-end воспроизведение с работающей установкой `codmap 0.0.46` и конфигурацией Devkit, которую этот путь реально принимает и сохраняет.

### 4.4. Что уже подтверждено небольшим экспериментом

В изолированном временном Git-репозитории:

```text
$ git ls-files tools/codemap
 tools/codemap

$ python -c 'from pathlib import Path; print(Path("tools/codemap").resolve())'
 /usr/bin/bash
```

Смоделированная по исходникам функция `_tracked()` вернула `False`; `.is_file()` вернул `True`; basename исходного пути — `codemap`. Данный результат **не** является запуском настоящего `pin_problem()` из установленного пакета и **не** подтверждает прохождение всей цепочки Devkit; он подтверждает механизм ошибочного выбора пути для Git-проверки.

### 4.5. Предпосылки и границы

- Нужен контроль над теми проектными файлами, из которых Devkit принимает команду `pin`, либо возможность подменить их до `status/update`.
- Чтобы ссылка на внешний Bash была доступна по абсолютному пути, она должна существовать в файловой системе после checkout и быть разрешаемой `Path.is_file()`.
- Для закрепления в хуке необходимо прохождение штатной логики обновления артефактов Devkit; это отдельный проверяемый шаг.
- Сам `.mcp.json` также может использоваться внешним MCP-клиентом: этот риск отделён от ответственности Codemap. Здесь рассматривается **то, что Codemap выполняет или записывает самостоятельно**.
- Проверка `git ls-files` по разрешённому пути — не единственная проблема модели: совпадение basename `codemap` само по себе не доказывает происхождение двоичного файла.

### 4.6. Исправление

**Минимальное локальное исправление:**

1. Проверять принадлежность Git **исходного лексического пути** (например, `tools/codemap`) до `resolve()`, а не только конечного файла.
2. Явно отклонять symlink как `pin` из проектной `.mcp.json`, если есть риск интерпретации его как доверенного исполняемого файла.
3. Если symlink должен поддерживаться (типичный сценарий виртуальных окружений), разрешать его только в рамках доверенной модели происхождения: например, валидировать ожидаемую установку или принимать `pin` лишь из локально доверенного состояния пользователя.
4. Добавить тест на индексированный symlink на внешнее приложение, путь `status/update`, отсутствие исполнения и отсутствие сохранения в post-commit hook.

**Более сильное исправление границы доверия:** не «реабилитировать» исполнение из `.mcp.json` набором правил по имени файла. Для `status/update` использовать исполняемый файл из **запущенной доверенной установки Codemap** либо отдельную явно доверенную пользователем запись, не заимствуемую автоматически из репозитория. Тогда проектный файл становится декларацией настройки MCP, а не источником кода для запуска Devkit.

## 5. Дополнительная находка FU-02: несоответствие проверяемого и исполняемого `-o` в `refresh`

**Связь с исходным аудитом:** F-06.  
**Подсистема:** CLI / sidecar `.meta.json` / `refresh`.  
**Предварительный приоритет:** **P2**, целостность выходных файлов.  
**Доказательность:** контрпример непосредственно следует из исходников, поведение argparse подтверждено независимым минимальным экспериментом; полный `refresh` не запускался.

### 5.1. Обещанная граница доверия

В ответе разработчика справедливо сказано, что исходная рекомендация была недостаточна: мало проверить, что записанный в sidecar рецепт запускает `build`, нужно проверить, что он пишет **тот же граф**, который пользователь передал команде `refresh`.

В `0.0.46` появилась функция [`_recipe_problem()`](https://github.com/kogriv/codemap/blob/32a7a64/codemap/cli.py#L911-L928), где выходной путь извлекается так:

```python
out = next(
    (argv[i + 1] for i, a in enumerate(argv[:-1]) if a in ("-o", "--out")),
    None,
)
out = out or next((a.split("=", 1)[1] for a in argv if a.startswith("--out=")), None)
```

Затем проверяется абсолютное разрешение `cwd/out` относительно `graph`. Если совпадает — `_cmd_refresh()` вызывает `main(meta["argv"])`.

### 5.2. Проблема

`next(...)` выбирает **первый** `-o/--out`. Но определение [`build` через argparse](https://github.com/kogriv/codemap/blob/32a7a64/codemap/cli.py#L1391-L1396) задаёт обычный параметр с одним значением, а не `append`; при нескольких вхождениях сохраняется **последнее**.

В результате проверяющая функция и исполняющая функция **не эквивалентны по семантике**.

### 5.3. Конкретный рецепт

Содержимое sidecar возле `/project/graph.json`:

```json
{
  "argv": [
    "build", "pkg",
    "-o", "graph.json",
    "-o", "../other.json"
  ],
  "cwd": "/project"
}
```

Порядок шагов:

1. `_recipe_problem()` видит первую пару `-o graph.json`.
2. `/project/graph.json` совпадает с переданным `refresh` — проверка возвращает `None`.
3. `_cmd_refresh()` запускает `main(meta["argv"])`.
4. `argparse` разрешает дублирующийся `-o` в пользу `../other.json`.
5. При успешной сборке граф записывается в `/project/../other.json`, а не в исходный граф.

Сценарий не требует исполнения shell-кода: это дефект контроля **побочного эффекта** `build`. Если каталог или файл доступны на запись, итогом может стать перезапись другого JSON-файла. Для утверждения о перезаписи конкретного защищённого файла необходимо отдельное end-to-end испытание и проверка разрешённых путей/прав процесса.

### 5.4. Проверка минимального механизма

Независимая проверка обычного `argparse` в Python 3.13:

```python
import argparse
p = argparse.ArgumentParser()
p.add_argument("-o", "--out")
a = p.parse_args(["-o", "graph.json", "-o", "../other.json"])
assert a.out == "../other.json"
```

Вывод: `../other.json`.

Существующий [тест `test_e4_refresh_repeats_only_a_build_of_this_graph`](https://github.com/kogriv/codemap/blob/32a7a64/tests/test_r1c125_graph_trust.py) проверяет одиночные выходные аргументы и запрещённую операцию `export`, но **не проверяет конфликтующие повторения**.

### 5.5. Исправление

**Предпочтительный вариант:** разбирать аргументы записанного рецепта тем же `argparse`-парсером, что использует `main()`, без его исполнения, и проверять результат парсинга (`command == "build"`, эффективный `out == graph`). Разбор должен быть безопасным при ошибках (`SystemExit`, некорректные типы, конфликтующие значения).

**Более простой достаточный вариант:** запретить все повторения `-o` и `--out`, включая `--out=...`, и принимать только одну однозначную форму. Тогда проверка становится сильнее обычного CLI, но рецепт строится приложением и не обязан поддерживать избыточный синтаксис.

Дополнительно полезно рассматривать рецепт как структурированные данные (`command`, `path`, `out`, `mode`, `consumer`, `docs`) с проверкой схемы, а не как произвольный массив `argv`, который позже снова парсится.

### 5.6. Регрессионные ожидания

| ID | Ожидание |
|---|---|
| FU-02-E1 | `-o graph.json -o ../other.json` отвергается |
| FU-02-E2 | `--out=graph.json --out=../other.json` отвергается |
| FU-02-E3 | Смешанные формы `-o` и `--out=...` отвергаются или валидируются по **фактическому** итоговому значению |
| FU-02-E4 | Обычный сохранённый рецепт `build pkg -o graph.json` продолжает работать |
| FU-02-E5 | При отказе не выполняется `build` и не изменяется ни целевой граф, ни посторонний файл |
| FU-02-E6 | Тест делается как для `_recipe_problem()`, так и через реальный CLI `refresh` |

## 6. Дополнительная находка FU-03: гонка поколений в кэше `advise`

**Связь с исходным аудитом:** F-11.  
**Подсистема:** кэш `advise`, генерации `gen-*`, `current`.  
**Предварительный приоритет:** **P2 при поддерживаемых конкурентных обновлениях; иначе P3**.  
**Доказательность:** последовательность гонки выводится из исходного алгоритма; не выполнялся детерминированный многопроцессный прогон.

### 6.1. Что исправлено правильно

До `0.0.46` обновление `matrix.toml` и `feed.json` записывало файлы по очереди, из-за чего при прерывании можно было получить смешанное поколение. Новая функция [`publish_pair()`](https://github.com/kogriv/codemap/blob/32a7a64/codemap/advise/refresh.py#L60-L85) сначала записывает оба файла в отдельную директорию, а затем атомарно переключает файл `current`.

Это корректное улучшение относительно исходной F-11: **одна публикация** не открывает читателям частично записанную новую пару.

### 6.2. Как устроено удаление

```python
atomic.write_bytes(gen / "matrix.toml", mraw)
atomic.write_bytes(gen / "feed.json", fraw)
atomic.write_text(cdir / CURRENT, gen.name + "\n")

for old in cdir.glob("gen-*"):
    if old.is_dir() and old.name != gen.name:
        shutil.rmtree(old, ignore_errors=True)
```

После переключения каждый publisher удаляет **все поколения, кроме созданного им**. Протокол не содержит межпроцессной блокировки; запись `current` сама по себе не синхронизирует последующую очистку.

### 6.3. Контрпример: два издателя

Пусть процессы A и B обновляют один и тот же cache directory и создают `gen-A`, `gen-B`:

| Шаг | Процесс A | Процесс B | `current` |
|---|---|---|---|
| 1 | Создал `gen-A` | — | старое поколение |
| 2 | — | Создал `gen-B` | старое поколение |
| 3 | Публикует `current=gen-A` | — | `gen-A` |
| 4 | — | Публикует `current=gen-B` | `gen-B` |
| 5 | Удаляет `gen-B` как чужое поколение | — | `gen-B`, но каталога уже нет |
| 6 | — | Удаляет `gen-A` как чужое поколение | `gen-B`, каталога нет |

Атомарность `os.replace()` здесь соблюдена на каждом отдельном шаге, но состояние **системы из указателя и каталогов** некорректно. Следующая загрузка читает `current=gen-B` и не находит каталога.

### 6.4. Контрпример: читатель и очистка

[`_served_dir()`](https://github.com/kogriv/codemap/blob/32a7a64/codemap/advise/__init__.py#L107-L114) читает имя поколения и возвращает путь. Затем [`load()`](https://github.com/kogriv/codemap/blob/32a7a64/codemap/advise/__init__.py#L140-L150) читает два файла в этом каталоге.

Если читатель уже получил путь к старому `gen-A`, а издатель сразу после публикации нового `gen-B` удалил `gen-A`, чтение может завершиться `FileNotFoundError` для отдельных файлов. По текущей логике `_read_pair()` такая ошибка местами подавляется и может привести к откату на packaged catalog или неполному чтению кэша, а не к сохранению гарантированно предыдущего поколения.

### 6.5. Почему обычный тест не выявил проблему

Тест [`test_e2_a_failure_between_the_two_files_keeps_the_old_pair`](https://github.com/kogriv/codemap/blob/32a7a64/tests/test_r1c124_atomic_writes.py) проверяет сбой при записи второго файла **до** переключения `current`, но не распараллеливает два `publish_pair` и не удерживает читателя на старом каталоге.

Для заявленной гарантии «читатель всегда видит целое старое либо целое новое поколение» этого недостаточно.

### 6.6. Варианты исправления

1. **Сериализовать публикующие процессы** межпроцессной блокировкой на один cache directory: подготовка → переключение → согласованная сборка мусора.
2. **Не удалять старые поколения немедленно.** Оставлять небольшой запас (например, последние N поколений и/или возрастной grace period) с отдельным безопасным GC. Это важно, потому что одна блокировка писателей **не предотвращает** гонку с уже читающим процессом.
3. Читателю передавать не только путь, но и согласованный жизненный цикл поколения; либо читать с retry на смену `current`/отсутствие каталога и применять явную fallback-политику.
4. Обрабатывать повреждённый или устаревший `current` как диагностируемую ситуацию, а не молчаливо считать публикацию успешной.

Для редко вызываемого ручного `advise --refresh` риск практической эксплуатации может быть невысок. В этом случае приоритет допустимо снизить до P3, но либо задокументировать ограничение конкурентности, либо исправить заявленную гарантию.

### 6.7. Регрессионные ожидания

| ID | Ожидание |
|---|---|
| FU-03-E1 | Два процесса с одной cache directory не оставляют `current` на удалённом поколении |
| FU-03-E2 | После успешной публикации оба файла указанного поколения доступны и валидны |
| FU-03-E3 | Читатель, начавший чтение старого поколения до переключения, не получает смешанную/отсутствующую пару |
| FU-03-E4 | Сбой до переключения не изменяет предыдущее поколение (существующая гарантия сохраняется) |
| FU-03-E5 | Совместимость со старой парой на верхнем уровне каталога остаётся проверенной |

## 8. Разбор основных возражений разработчика

### 8.1. F-13: `unknown` и `behind` нельзя смешивать

Возражение обоснованно. Отсутствие возможности подтвердить соответствие графа источникам не идентично доказанному устареванию. Если `check` в обычном режиме отказывает только при `behind`, это может быть намеренной политикой, а не багом. Для строго регулируемых CI нужен опциональный fail-closed режим, и его сделали через `--require-current`.

Первая рекомендация «добавить строгий режим в CI devkit» была плохо адресована: шаблон devkit строит граф в том же задании перед `check`, поэтому именно там неопределённость обычно не возникает. Я принимаю это уточнение.

### 8.2. F-15: верхние границы библиотечных зависимостей

Жёсткие верхние границы транзитивных зависимостей в обычной Python-библиотеке могут создавать конфликты зависимостей и ухудшать совместимость с приложениями потребителей. С этим возражением согласен.

Однако полезно различать:

- **публичные runtime constraints библиотеки:** минимальные совместимые версии и обоснованные исключения;
- **тестовое окружение CI:** при необходимости зафиксированные или матричные зависимости для воспроизводимости и раннего выявления регрессий;
- **цепочку поставки:** SHA-pin GitHub Actions, проверка скачиваемых бинарных артефактов, сканирование известных уязвимостей.

Согласно исходникам CI `0.0.46`, Actions закреплены по commit SHA, введён `pip-audit`, а сторонний архив SCIP проверяется по digest. Это конкретные полезные изменения.

### 8.3. F-16: оценочный токен-бюджет

Справедливо: функция названа `estimate_tokens`, в docstring уже была оценка порядка 4 символов на токен. Главная проблемная часть — сильное утверждение документации, будто любой результат гарантированно не превышает реальный бюджет модели. Уточнение смысла оценки и требование запаса — адекватное исправление. Новое поле в ответе и смена `ANSWER_FORMAT` не обязательны.

### 8.4. F-05: блокировка против immutable snapshot

Потоковая гонка с `Session._resolution`, `_limit`, `_filter`, `_scope` и заменой `graph/query` действительно может устраняться одной сессионной блокировкой на весь запрос. Отдельный request context и неизменяемый snapshot больше подходят, когда станет необходимым параллельное выполнение запросов и можно измерить блокировку как bottleneck. В текущем масштабе это **архитектурный выбор**, а не неполное исправление F-05.

### 8.5. F-09: предел маркерной проверки

В релизной сверке 0.0.46 для `package: "pkg;touch M"` указано, что старый маркер создавался «by the still-tampered pin». Поэтому этот конкретный тест нельзя трактовать как чистое доказательство командной инъекции **только** за счёт необработанного `package`.

Тем не менее ранний код подставлял значения в shell/YAML без экранирования; исправление двойным барьером соответствует выявленной проблеме. Правильное описание доказательств: **дефект кода подтверждён**, а конкретный маркерный тест **не изолирует причину** в старой версии.

## 9. Дополнительные риски, найденные и описанные самим разработчиком

Реакция проекта выявила больше, чем содержал первый аудит. Это не основания игнорировать исходный аудит, а полезные дополнения к его модели угроз.

| Дополнительная проблема в ответе проекта | Оценка |
|---|---|
| `devkit update` переносил подменённый pin в post-commit hook, превращая разовое исполнение в повторяющееся | Существенное усиление F-01; не было выявлено исходным аудитором. FU-01 показывает, почему эту цепочку нужно дополнительно проверить на обходы. |
| `pin_has_mcp` мог запускать интерпретатор из shebang файла pin | Дополнительный источник исполнения через недоверенный путь, не отражённый в первоначальной находке. |
| Неэкранирован был и `{{graph}}`, не только `{{package}}` | Расширяет F-09; устранено через форматирование shell-аргументов. |
| Запасной `python -m codemap` импортировал бы локальный `codemap/` из корня репозитория | Существенная уязвимая граница импортов; переход на `python -I -m codemap` обоснован. |
| Эвристика диспетчера `import_module/getattr` шире, чем входивший в первый снимок механизм | Это не обязательно баг, но архитектурный источник ложноположительных рёбер: требуется сохранять маркировку эвристичности. |

Наличие этих дополнительных пунктов увеличивает доверие к качеству инженерного разбора: разработчик самостоятельно расширил угрозовую модель. Одновременно это напоминает, что закрытие одной известной exploitation string не равнозначно устранению всего класса недоверенного исполнения.

## 11. Приоритизированная программа исправлений

### P1 — FU-01: устранить доверие к имени `pin` из проектного файла

**Критерий готовности:** Devkit не исполняет и не закрепляет в хуке произвольный файл, полученный из `.mcp.json`, даже если файл называется `codemap`, находится за symlink или индексирован как ссылка Git. Нормальный installed CLI и, при необходимости, явно доверенная локальная `.venv` сохраняют работоспособность.

**Проверки:** отдельный unit test `pin_problem()`; интеграционный тест `devkit status/update`; безопасный end-to-end тест post-commit с маркером; тесты на symlink target, path alias, реальный файл Git и консольный скрипт.

**Последовательность:** сначала воспроизвести FU-01 без побочных эффектов, записать минимальный тест; затем выбрать trust model, исправить код; удалить защиту/вернуть старый путь в изолированном mutation test и убедиться, что тест краснеет; наконец проверить на собранном wheel.

### P2 — FU-02: сделать проверку рецепта семантически эквивалентной исполнению

**Критерий готовности:** невозможно передать JSON recipe, который успешно проходит `_recipe_problem()`, но при вызове `main(meta["argv"])` пишет граф в другой путь. Желательно не только для повторов `-o`, но и для любых поддерживаемых синтаксических форм `--out`.

**Проверки:** параметризованные unit tests и end-to-end тест `refresh` с посторонним sentinel-файлом. Синтаксически неоднозначные рецепты лучше отклонять, даже если `argparse` технически принимает их.

### P2/P3 — FU-03: согласовать публикацию, GC и чтение поколений

**Критерий готовности:** конкурентная публикация не оставляет `current` на удалённой директории; текущий читатель получает согласованную пару; единичный сбой записи сохраняет старое поколение.

**Проверки:** два независимых процесса, барьер после записи `current`, контроль каталогов после завершения; читатель с барьером между `_served_dir()` и `_read_pair()`; сценарии аварийной остановки и очистки предыдущих поколений.

### Отдельные продуктовые исследования — сохранять в бэклоге

| Задача проекта | Почему нужна | Что считать завершением |
|---|---|---|
| **R1-C130:** бенчмарк масштабируемости | Текущие оценки производительности сделаны на ограниченных деревьях | Не менее трёх классов проектов; P50/P95 задержки, RSS, размер графа, CPU/IO, режимы fast/deep/watch |
| **R1-C131:** кэш ранжирования | Без измеренного bottleneck кэш PageRank будет предположением | Профиль повторных запросов, доля попаданий, выигрыш/память, стратегия инвалидирования |
| **R1-C132:** независимая точность графа вызовов | Самоизмерение и проектные фикстуры не гарантируют переноса точности на чужой код | Независимые проекты и runtime/reference ground truth, понятные метрики precision/recall и область их применимости |

Из этих трёх **R1-C132** важнее всего для проверки центрального продукта: насколько Codemap позволяет доверять зависимостям и impact analysis за пределами собственных тестов.

## 12. Требования к подтверждению закрытия follow-up

Предлагаемый минимальный процесс, который можно приложить к последующему release engineering документу:

1. **Зафиксировать версию и среду:** точный Git SHA, Python, ОС, способ установки (`wheel`/editable) и путь тестового репозитория.
2. **Записать негативные ожидания до правки:** FU-01-E1…E6, FU-02-E1…E6, FU-03-E1…E5.
3. **Показать старую ошибку безопасным тестом:** маркер вместо произвольного действия, sentinel-файл вместо ценной пользовательской информации, искусственные поколения кэша вместо рабочего каталога.
4. **Исправить и показать защиту:** те же входы не приводят к нежелательным эффектам; валидные сценарии продолжают работать.
5. **Провести mutation check** на ключевую защиту, а не только на отдельную ветку теста.
6. **Запустить полную матрицу и сборку wheel** и отдельно проверить сценарии на установленной из релизного артефакта версии.
7. **Зафиксировать результат** ссылками на CI, коммит, тест, контрпример, а также отметить то, что сознательно не устраняется.

## 13. Исправления методики аудита на будущее

Первый аудит выявил реальные проблемы, однако его доказательная часть была неоднородной. Это требует не оправданий, а изменения стандарта формулировок.

### 13.1. Уровни доказательства

- **Подтверждено кодом:** есть точная ветка выполнения, контроль входов и отсутствие нужной проверки. Это сильнее общего предположения, но может пропускать внефайловые инварианты и условия вызова.
- **Подтверждено независимым воспроизведением:** вход приводит к наблюдаемому эффекту на зафиксированной версии; это сильнейшее основание для определения конкретного дефекта.
- **Подтверждено CI проекта:** тест существует и запуск завершился успешно, но проверка ограничена охваченными тестами и зависима от инфраструктуры проекта.
- **Заявлено в release notes:** полезный источник технической истории, но он не заменяет независимый запуск.
- **Гипотеза производительности или эксплуатации:** требует условий, бенчмарка и контрольной выборки; нельзя превращать её в установленный факт по одному месту в коде.

### 13.2. Приоритет — отдельно от определённости

Высокий **потенциальный ущерб** не означает автоматически высокую **уверенность в воспроизводимости**. Так, FU-01 получило предварительный P1 потому, что возможен переход от чужого проектного файла к исполнению команды на машине разработчика, но окончательный статус зависит от полного Devkit reproducer. Для FU-03, где ущерб прежде всего связан с кэшем, частота конкурентного обновления непосредственно влияет на практический приоритет.

### 13.3. Для релизных утверждений нужен полный контур свидетельств

Не делать вывод «релиз с красным CI», пока не проверены:

1. **SHA фактически опубликованного тега** (включая развёртку annotated tag до commit),
2. **финальный CI именно этого SHA**,
3. **состояние опубликованного пакета** и его привязка к исходникам,
4. **хронология публикации**.

История F-12 — пример ошибки от остановки на промежуточном коммите, не ошибки проекта в фактически опубликованной версии.

## 14. Окончательный вердикт

**Разработчик представил сильный, проверяемый и в значительной части корректный ответ на первоначальный аудит.** Ряд возражений принимается полностью: F-12, принципиальная постановка F-13, оценка тяжести F-16 и выбор блокировки для F-05. По F-15 верна критика автоматического требования верхних границ зависимостей библиотеки; одновременно полезность улучшений supply chain очевидна.

**Исходные дефекты действительно привели к существенным изменениям релиза `0.0.46`.** Но более строгое тестирование нескольких доверительных границ всё ещё необходимо. Повторное чтение кода выявило три конкретных сценария, которые не входят в опубликованную матрицу регрессии. Их следует рассмотреть как **новые follow-up**, а не как повод считать бесполезным весь объём проделанных исправлений.

### Предлагаемый статус по исходному аудиту

- **F-12:** официально исправить заключение первоначального аудитора — претензия к опубликованному CI отозвана.
- **F-05, F-13, F-15, F-16:** зафиксировать принятые аргументы разработчика и уточнённую постановку.
- **Остальные исходные F:** считать их первоначальные воспроизводимые сценарии исправленными **по представленным исходникам и проектным тестам**, с исключением областей, где FU-01…FU-03 обнаружили дополнительные обходы или конкурентные условия.
- **FU-01, FU-02, FU-03:** открыть отдельно, провести независимое end-to-end воспроизведение, затем исправить или аргументированно опровергнуть на конкретном состоянии кода.

**Итог:** инженерная зрелость проекта по результатам реакции на аудит оценивается выше, чем в первом заключении; безопасность Devkit для недоверенных репозиториев пока нельзя считать исчерпывающе доказанной. Самый важный следующий шаг — проверка и устранение FU-01. Самое важное продуктовое исследование — независимый бенчмарк точности графа вызовов R1-C132.

## Приложение A. Минимальные безопасные репродукторы механизмов

Примеры не запускают вредоносных команд и не затрагивают пользовательские файлы. Их результат иллюстрирует **механизм**, а не заменяет интеграционные тесты установленного Codemap.

### A.1. Git symlink + `Path.resolve`

```python
from pathlib import Path
import subprocess
import tempfile

with tempfile.TemporaryDirectory() as tmp:
    root = Path(tmp)
    subprocess.run(["git", "init", "-q", str(root)], check=True)
    (root / "tools").mkdir()
    link = root / "tools" / "codemap"
    link.symlink_to("/bin/bash")  # существующий Bash; используется лишь для проверки пути
    subprocess.run(["git", "-C", str(root), "add", "tools/codemap"], check=True)

    def tracked_as_in_0_0_46(path):
        try:
            rel = path.resolve().relative_to(root.resolve())
        except ValueError:
            return False
        return subprocess.run(
            ["git", "-C", str(root), "ls-files", "--error-unmatch", "--", str(rel)],
            capture_output=True,
        ).returncode == 0

    indexed_link = subprocess.run(
        ["git", "-C", str(root), "ls-files", "--error-unmatch", "--", "tools/codemap"],
        capture_output=True,
    ).returncode == 0

    assert indexed_link is True
    assert link.name == "codemap"
    assert link.is_file()
    assert tracked_as_in_0_0_46(link) is False
```

На некоторых ОС путь `/bin/bash` разрешается в `/usr/bin/bash`; это не влияет на результат — оба варианта находятся вне временного репозитория. На Windows нужен аналогичный существующий исполняемый файл и доступная поддержка Git symlink.

**Следующий реальный тест:** с установленным `codmap==0.0.46` импортировать `codemap.devkit.install.pin_problem` и проверить, что это значение `pin` отвергается. В `0.0.46` чтение кода предсказывает обратное; результат должен быть зафиксирован фактическим прогоном, а не подменён симуляцией.

### A.2. Несовпадение первого `-o` и результата `argparse`

```python
import argparse

argv = ["build", "pkg", "-o", "graph.json", "-o", "../other.json"]

first_out = next(
    (argv[i + 1] for i, value in enumerate(argv[:-1]) if value in ("-o", "--out")),
    None,
)

parser = argparse.ArgumentParser()
parser.add_argument("command")
parser.add_argument("path")
parser.add_argument("-o", "--out")
actual = parser.parse_args(argv)

assert first_out == "graph.json"
assert actual.out == "../other.json"
```

**Следующий реальный тест:** создать минимальный `pkg`, построить `graph.json`, подменить `.meta.json` конфликтующим рецептом; проверить, что `refresh` отказывает до сборки и не изменяет посторонний sentinel-файл. На текущем релизном коде ожидается нарушение этой гарантии.

### A.3. Сценарий для многопроцессного теста `publish_pair`

Контрольный тест должен организовать барьеры между шагами `atomic.write_text(cdir / "current", ...)` и последующим `glob("gen-*")` для **двух** независимых процессов. После того как оба указателя были заменены, обе очистки должны завершиться. Инвариант:

```python
name = (cache_dir / "current").read_text().strip()
assert (cache_dir / name / "matrix.toml").is_file()
assert (cache_dir / name / "feed.json").is_file()
```

Второй тест должен удержать читателя на уже прочитанном имени поколения и разрешить издателю выполнить очистку. Проверка: читатель получает валидную согласованную пару или явно управляемый retry, а не отсутствие целевого каталога.
