> *English summary.* All three new findings are real. Each was reproduced end to end on 0.0.46, not only in its
> mechanism. FU-01: the hook was pinned to a committed link `tools/codemap → /bin/sh`, and a commit ran the
> committed `build` script. FU-02: `codemap refresh` wrote the graph to another file. Two more shapes were found
> here besides the audit's: an abbreviated `--ou`, and a recorded working directory that does not exist.
> FU-03: `current` named a removed generation, and the cache fell back to the packaged catalog without a word.
> Fixes: FU-01 asks git about the path as written and about every directory on it, judges a console script by its

> that runs it. FU-03 removes a generation only when `current` does not name it and it is older than ten minutes,
> retries a split read, and reports a dangling pointer. The release check repeats each reproduction on 0.0.46
> from PyPI and shows it absent on the next release. FU-01 gets its own advisory, since it bypasses the fix of
> GHSA-c3hp-596c-2p77. The audit's criticism of the 0.0.46 F-09 probe is accepted, and an isolated probe is
> recorded in the release check.

## 1. Как проверялось

Аудитор честно разделил «подтверждено кодом» и «доказано запуском» (§2.3, §12.1) и попросил второе. Здесь всё —
второе. Каждый FU воспроизведён на коде 0.0.46 до правки, целиком, с безобидным маркером или посторонним файлом:

- **FU-01**: `devkit init` → в git добавлены ссылка `tools/codemap → /bin/sh` и скрипт `build`, который создаёт
  маркер → `.mcp.json` называет `<корень>/tools/codemap` → `devkit update` записал в хук
  `C=<корень>/tools/codemap` → запуск хука создал маркер.
- **FU-02**: настоящий `codemap refresh` из другого каталога с подменённым sidecar записал `other1.json`,
  `other2.json`, `other3.json` рядом с графом (по одному на форму). Для записанного несуществующего `cwd` граф ушёл
  в другой каталог, и `build` этот каталог ещё и создал.
- **FU-03**: два `publish_pair` в потоках, сведённые барьером сразу после записи `current`. В итоге в каталоге кэша
  остался только `current`, а `_served_dir` вернул корень кэша.

Затем по обычному порядку проекта:

1. ожидания записаны в бэклог отдельным коммитом **до** кода (`c3e6877`);
2. код исправлен, тесты написаны;
3. каждая защита снята по отдельности, и упал ровно её тест;
4. старый код роняет новые тесты, в том числе сквозной тест хука сам по себе.

Выпуск сверяется с PyPI в чистых окружениях, протокол — в
[`release_engineering.md`](../design/release_engineering.md).

### FU-01 — пин через ссылку, которую несёт репозиторий

**Что было не так.** `_tracked` спрашивал git о пути после `resolve()`. Если цель ссылки лежит вне корня, ответ
«не отслеживается». Наш тест R1-C121 проверял обычный закоммиченный файл, то есть **форму** атаки, а не её
**класс** — «всё, что выбрал тот, кто пушил». Та же ошибка, от которой у нас есть правило «каждое исключение — со
своим зондом».

**Предпосылка, которой нет в аудите.** Пин должен быть абсолютным. Значит, `.mcp.json` атакующего должен назвать
путь, по которому жертва держит checkout. Это возможно (типовые пути, единая раскладка в команде, CI-раннер), но
это условие. Тяжесть мы всё равно оцениваем как высокую: последствие то же, что у F-01, — команда на каждом
коммите.

**Исправление** (`codemap/devkit/install.py`, `_carried`, `_console_script_problem`):

1. git спрашивается о пути **как он написан** (`..` свёрнуты, ссылки не раскрыты) и о **каждом каталоге на нём**,
   с `--literal-pathspecs`. Ссылка-файл `tools/codemap`, ссылка-каталог `tools → …`, подмодуль — всё это
   «несёт репозиторий». Разрешённый путь спрашивается тоже: это ссылка снаружи внутрь.
2. Консольный скрипт принимается по **содержимому**: он начинается с `#!` и запускает `codemap.cli`. Имя больше
   ничего не доказывает (§4.5 аудита). Копия `/bin/sh` под именем `codemap` вне репозитория отвергается.
3. Корень не git-репозиторий, а пин внутри корня — отказ: нельзя сказать, кто его написал.
4. Пин, который пишет сам codemap (`running_pin`), проходит ту же проверку содержимого. Иначе `init`, запущенный
   через обёртку, записал бы пин, который следующий `status` отвергнет.

Тесты: `tests/test_r1c133_pin_links.py`. В него входит FU-01-E6 аудита — запуск **настоящего** хука с
закоммиченным `build`; на старом коде он краснеет сам, без проверки `pin_problem`. Каждая из четырёх защит снята по
отдельности и роняет свой тест. `.venv/bin/python` (ссылка на системный python) и неотслеживаемый
`.venv/bin/codemap` по-прежнему принимаются.

**Чем это отличается от рекомендаций §4.6.**

- **Пункт 2 «отклонять ссылки»** не взят. Python в виртуальном окружении — ссылка, это обычная установка.
  Отклоняется не ссылка, а ссылка, которую несёт репозиторий.
- **«Более сильное исправление»** (вообще не брать пин из `.mcp.json`) рассмотрено и не взято. Пин в `.mcp.json` —
  то, как проект называет свой codemap (например, из `.venv`). После правки доверие сводится к явному
  предположению: принимается только файл, который **создал локальный пользователь**:
  - вне репозитория или неотслеживаемый внутри;
  - не через отслеживаемый каталог или ссылку;
  - консольный скрипт codemap по содержимому.

  Push такой файл создать не может. Если это предположение когда-нибудь окажется ложным, следующий шаг — то, что
  предлагает аудит: пин только из пользовательского состояния вне репозитория.
- **Windows:** для `codemap.exe` содержимое проверяется поиском `codemap.cli` в лаунчере. Лаунчеры pip и uv несут
  скрипт несжатым zip, но на Windows это не проверено. Если проверка ошибётся, пин будет отвергнут с нотой, и
  devkit возьмёт запущенный codemap. Это безопасная сторона.

**Advisory.** FU-01 обходит исправление GHSA-c3hp-596c-2p77, поэтому затронута и 0.0.46. Отдельный advisory —
[GHSA-mjvh-v399-r45r](https://github.com/kogriv/codemap/security/advisories/GHSA-mjvh-v399-r45r) (high, 0.0.46, исправлено в 0.0.47): у тех, кто уже обновился до 0.0.46, должно сработать новое
предупреждение. Выпуск сверен с PyPI: каждая проба воспроизводится на 0.0.46 и отсутствует на 0.0.47.

### FU-02 — проверка рецепта не равна его исполнению

**Шире, чем в аудите.** Кроме повторного `-o` и `--out=`, прошли ещё две формы:

- **Сокращение `--ou x`.** argparse по умолчанию принимает префиксы длинных опций; сюда же слитная форма `-oX`.
- **Записанный `cwd`, которого нет.** Проверка считала путь от записанного каталога, а исполнение, не найдя его,
  оставалось в текущем. Граф ушёл в другой каталог, и `build` его создал.

Корень один: мы написали второй, маленький парсер вместо того, чтобы спросить настоящий.

**Исправление** — предпочтительный вариант аудита (§5.5): рецепт разбирается тем же `build_parser()`, которым
`main` его исполнит, вывод argparse перехватывается. Сверяется итоговое `out`, и считается оно от того каталога,
где пойдёт сборка. Записанный `cwd`, который не каталог, — отказ. Эквивалентность проверки и исполнения теперь
держится построением, а не перечнем форм.

Не взяли:

- **Отдельный запрет повторов** не нужен, если сверяется итог разбора.
- **Структурированный рецепт вместо `argv`** — это смена формата sidecar ради того, что уже закрыто.

Тесты: `tests/test_r1c134_refresh_recipe.py`, все через настоящий `codemap refresh`; посторонний sentinel-файл не
тронут, новых файлов нет. На старом коде красные шесть из десяти: E1–E4 и E7. Смешанная форма `--out=… -o …` и
три контроля зелёные и до правки — старый код брал первую пару `-o`. Снятие проверки `cwd` роняет только E4.

### FU-03 — поколения кэша advise

**Последствие точнее.** Кэш не повреждается, смешанной пары из двух поколений нет. Происходит другое:

- **Два издателя.** Свежий каталог молча теряется до следующего `--refresh`, отдаётся встроенный.
- **Читатель во время чистки.** Он мог получить matrix из кэша и feed из пакета. `source` честно помечал каждую
  часть, но обещание из docstring R1-C124 нарушалось.

Приоритет P3, как и предлагает аудит для ручного еженедельного `--refresh`. Исправить дёшево, поэтому исправили, а
не задокументировали.

**Исправление** — варианты 2–4 из §6.6:

- **Чистка поколений** (`refresh.collect`): удаляется только поколение, которое `current` **сейчас** не называет и
  которое старше `GRACE_SECONDS` (десять минут).
- **Повтор чтения** (`load`): если один файл пары есть, а другого нет, чтение повторяется.
- **Висячий `current`** — нота в заголовке каталога, а не молчаливый откат.

Межпроцессная блокировка (вариант 1) не взята: она не защищает читателя (аудитор пишет то же) и требует отдельного
кода под каждую платформу.

Тесты: `tests/test_r1c135_advise_generations.py`. Каждая защита по отдельности роняет свой тест: окно, повторное
чтение `current`, повтор чтения, нота. Тест двух издателей краснеет на старом коде. Он зеленеет от любой из двух
защит — окна или повторного чтения `current`, — поэтому стоят обе.

## 3. Чего не хватало нашим тестам — и почему

Все три дыры прошли через наши же регрессионные тесты R1-C121, R1-C125 и R1-C124. Причина общая: тест закреплял
пример атаки, а не границу.

| Тест | Что проверял | Что должен был |
|---|---|---|
| R1-C121 | обычный закоммиченный файл как пин | всё, до чего дотянулся push: ссылку, каталог на пути, подмодуль |
| R1-C125 | одиночный `-o` | что проверка и исполнение читают рецепт одинаково |
| R1-C124 | один издатель, сбой между файлами | два издателя и читатель |

Урок для своих тестов: у граничной проверки должен быть тест, который строит вход **другим способом**, чем тот,
под который писалась защита. Правило про зонд для исключения теперь применяем и к проверкам доверия.
