## 2. Что представляет собой Codemap

Codemap — статический анализатор исходного кода Python, формирующий структурированный граф программного проекта.

Его задача существенно шире построения карты импортов. Продукт стремится отвечать на вопросы об API, зависимостях, циклах, связности, влиянии изменений, достижимости, вызовах функций и архитектурных ограничениях.

Важное архитектурное решение — отделение извлечения фактов из исходного кода от последующих запросов к графу.

### Логическая схема подсистем

```text
                     Исходники Python
              (core · tests · docs · consumers)
                             |
                             v
                          EXTRACT
                 AST · Griffe · Jedi · dataflow
                             |
                             v
                       GRAPH / STORE
                  nodes · edges · provenance
                             |
                             v
                    QUERY / ARCHITECTURE
                             |
                +------------+-------------+
                |            |             |
                v            v             v
             CLI / CI     MCP / Serve      Exports
```

Схема отражает логические отношения основных подсистем по исходникам репозитория.

### Архитектурные преимущества

В коде прослеживается несколько сильных инженерных решений:

- **Source-only extraction.** Анализируемый пакет не требуется импортировать или исполнять. Это снижает риск побочных эффектов при разборе чужих проектов, хотя не делает обработку произвольных файлов автоматически безопасной.
- **Единая графовая модель.** Разные представления работают поверх общей модели, уменьшая риск расхождения между инструментами анализа.
- **Разделение fast/deep.** Быстрый анализ и более дорогой анализ вызовов через Jedi не выдаются за равнозначные по точности.
- **Provenance.** Граф сопровождается информацией о происхождении и условиях построения, что важно для воспроизводимости результатов.
- **Явная неполнота.** В интерфейсе предусмотрены признаки неоднозначного разрешения, ограниченных выборок и неполноты результатов.
- **Проверяемые архитектурные контракты.** Проект применяет собственный анализатор к своей архитектуре через `codemap.toml` и CI.

Это хорошая основа для инструмента code intelligence, рассчитанного не только на человека, но и на программных агентов.

При этом ключевое требование к такому продукту выше, чем к обычному генератору документации: **неполный граф не должен приводить к уверенным, но ошибочным заключениям о безопасности изменения кода.** Именно это является главным критерием дальнейшего аудита.

## 3. Критические и высокоприоритетные замечания

### F-01. Выполнение команды из недоверенной конфигурации Devkit

**Приоритет: P1 — высокий риск.**  
**Статус:** подтверждённая цепочка выполнения по исходному коду; отдельный эксплуатационный тест не запускался.

Код:

- [`codemap/devkit/install.py`, строки 58–73](https://github.com/kogriv/codemap/blob/def00ce1/codemap/devkit/install.py#L58-L73)
- [`codemap/devkit/install.py`, строки 527–545](https://github.com/kogriv/codemap/blob/def00ce1/codemap/devkit/install.py#L527-L545)
- [`codemap/devkit/state.py`](https://github.com/kogriv/codemap/blob/def00ce1/codemap/devkit/state.py)

**Механизм.**

Devkit хранит сведения о своём состоянии в `.codemap-devkit.json`, а конфигурацию MCP читает из `.mcp.json`.

При выполнении `codemap devkit status` или `codemap devkit update` функция `_pin_and_version()` может извлечь из `.mcp.json` команду запуска Codemap.

Проверка допуска выглядит так:

```python
recorded = (st.get("artifacts", {}).get("mcp") or {}).get("sha256")
pin = pin_from_mcp(entry) if entry is not None and recorded is not None else None
```

Здесь проверяется **наличие сохранённого хэша, но не совпадение хэша с текущим содержимым MCP-конфигурации**.

Далее:

```python
out = subprocess.run(
    [*pin, "--version"],
    capture_output=True,
    text=True,
    timeout=30,
)
```

Значение `pin` может происходить из изменённого файла проекта, включая произвольное исполняемое имя и аргументы до `serve`.

Таким образом, проверка версии превращается в запуск команды из потенциально недоверенной конфигурации.

**Практический сценарий.**

Злоумышленник подготавливает репозиторий с изменёнными `.codemap-devkit.json` и `.mcp.json`. Разработчик выполняет безобидную на вид команду проверки Devkit. Codemap обращается к сохранённому исполняемому файлу и может запустить посторонний процесс.

Наличие `subprocess.run()` без `shell=True` не устраняет эту проблему: можно непосредственно выбрать исполняемый файл с аргументами выполнения кода.

**Последствия:** выполнение кода с правами пользователя, который запускает Devkit. Это особенно важно для AI coding agents, которые могут автоматически проверять состояние инструментов в клонированном проекте.

**Что исправить:**

1. Убрать выполнение команды, извлечённой из конфигурации проекта, из операций `status` и пассивной проверки.
2. Проверять фактический SHA-256 MCP-записи перед признанием её принадлежащей Devkit. Но считать это только проверкой согласованности, не защитой от злоумышленника, контролирующего оба файла.
3. Отделить доверенную команду запуска инструмента от проектной конфигурации MCP.
4. Запретить произвольные варианты запуска наподобие `python -c` в автоматически принимаемых pin-конфигурациях.
5. Добавить тест с подменённой `.mcp.json`, который подтверждает отсутствие запуска постороннего процесса.

**Приоритет:** исправить до рекомендации использовать Devkit на сторонних, не прошедших проверку репозиториях.

### F-02. Выход за пределы репозитория при работе с файлами Devkit

**Приоритет: P1 — высокий риск.**  
**Статус:** подтверждённая ошибка проверки путей; последствия зависят от прав файловой системы.

Код:

- [`codemap/devkit/install.py`, строки 163–199](https://github.com/kogriv/codemap/blob/def00ce1/codemap/devkit/install.py#L163-L199)
- [`codemap/devkit/install.py`, строки 224–272](https://github.com/kogriv/codemap/blob/def00ce1/codemap/devkit/install.py#L224-L272)
- [`codemap/devkit/artifacts.py`](https://github.com/kogriv/codemap/blob/def00ce1/codemap/devkit/artifacts.py)

Путь к файлу правил агента формируется следующим образом:

```python
MarkdownRegion(
    "agents",
    root / ctx["agents_file"],
)
```

`ctx["agents_file"]` поступает из сохранённого состояния проекта.

Не обнаружена проверка, что итоговый путь после нормализации остаётся внутри `root`.

Значение вроде:

```json
{"agents_file": "../../outside.md"}
```

может привести к обращению к файлу вне корня проекта.

Проблема усугубляется поведением `MarkdownRegion`: если в существующем файле отсутствует регион, помеченный Devkit, метод `current()` возвращает `None`, а `process()` может классифицировать его как новый управляемый артефакт. Запись затем добавляет блок в этот файл.

Следовательно, **`--force` не является надёжной защитой от изменения постороннего файла, выбранного через конфигурацию**.

Это не только риск перезаписи: возможны создание каталогов и изменение файлов вне проекта, доступных для записи пользователю.

**Исправление:** проводить каноникализацию путей через `resolve()`, проверять принадлежность разрешённому корню, отдельно обрабатывать символьные ссылки, отвергать абсолютные и выходящие наружу пути из сохраняемого состояния. Файлы вне корня должны требовать отдельного явного разрешения.

### F-03. Недостаточная изоляция файловых операций в MCP `source`

**Приоритет: P2 — существенный риск.**  
**Статус:** подтверждено чтением кода; эксплуатация зависит от возможности подменить граф.

Код: [`codemap/serve/session.py`, строки 814–836](https://github.com/kogriv/codemap/blob/def00ce1/codemap/serve/session.py#L814-L836).

Операция `source` возвращает исходный текст найденного символа:

```python
base = Path(self.source_root) if self.source_root else Path(".")
path = base / node.file
lines = path.read_text(encoding="utf-8").splitlines()
```

Значение `node.file` поступает из загруженного графа.

Вместе с тем [`Graph.from_dict()`](https://github.com/kogriv/codemap/blob/def00ce1/codemap/model.py#L392-L402) создаёт узлы из JSON без проверки допустимого расположения `file`.

Если загрузить специально подготовленный граф, содержащий абсолютный путь или `../`, операция `source` потенциально сможет прочитать текст вне указанного `source_root`.

Это не означает, что обычный граф Codemap содержит такие пути. Проблема проявляется на границе доверия к **загружаемому артефакту**.

Последствия становятся серьёзнее, если MCP-сервер используется агентом, который вправе обращаться к инструменту, но не должен читать произвольные файлы машины.

**Исправление:** после разрешения пути проверять его расположение внутри `source_root`, учитывать символьные ссылки, валидировать пути при загрузке графа и разделить разрешённые корни чтения по принципу минимальных привилегий.

Аналогичную проверку необходимо добавить к экспорту Obsidian: [`build_vault()`](https://github.com/kogriv/codemap/blob/def00ce1/codemap/serve/vault.py) формирует имена выходных файлов из идентификаторов узлов, а [`_write_vault()`](https://github.com/kogriv/codemap/blob/def00ce1/codemap/cli.py#L1275-L1280) записывает их без проверки выхода за границы каталога назначения. Для специально подготовленного графа это создаёт отдельный риск записи вне целевого каталога.

### F-04. Корректный JSON способен завершить процесс `serve`

**Приоритет: P2. Статус:** подтверждено статическим анализом.

[`codemap/serve/server.py`, строки 26–44](https://github.com/kogriv/codemap/blob/def00ce1/codemap/serve/server.py#L26-L44) принимает построчные JSON-запросы.

```python
request = json.loads(line)
response = session.handle(request)
```

Но [`Session.handle()`](https://github.com/kogriv/codemap/blob/def00ce1/codemap/serve/session.py#L390-L411) начинает обработку с:

```python
op = request.get("op")
args = request.get("args") or {}
```

Причём эти операции находятся вне `try`.

JSON допускает не только объекты, но и массивы, числа, строки и `null`. Например, строка `null` успешно проходит `json.loads()`, после чего вызов `request.get()` вызывает `AttributeError`.

Исключение не перехватывается транспортным циклом. Значит, заявленное поведение «ошибка запроса не завершает резидентный процесс» нарушается.

Для проверки достаточно подать в работающий stdio-сервер последовательно:

```text
null
{"op":"stats"}
```

**Ожидаемое правильное поведение:** первый запрос получает структурированную ошибку, второй обрабатывается нормально.

**Следствие текущей реализации:** процесс может завершиться на первом запросе.

Исправление состоит из проверки типа верхнего уровня, проверки типа `args` и переноса всей обработки внутрь защищённой границы. Нужен отдельный параметризованный тест с `null`, `[]`, `42`, `"text"` и корректным объектом с некорректными аргументами.

### F-05. Гонки состояния между запросами и автоматической перезагрузкой

**Приоритет: P2. Статус:** подтверждённая небезопасная конструкция; воспроизводимость гонки не измерена.

В [`Session`](https://github.com/kogriv/codemap/blob/def00ce1/codemap/serve/session.py) хранятся общие изменяемые поля:

`self.graph`, `self.query`, `self._resolution`, `self._limit`, `self._filter`, `self._scope`, `self._currency_cache`.

Один запрос устанавливает некоторые поля, выполняет операцию, а затем читает эти же поля для формирования ответа.

Одновременно [`_start_reload_watcher()`](https://github.com/kogriv/codemap/blob/def00ce1/codemap/cli.py#L1224-L1264) запускает отдельный поток, который может вызвать `session.handle({"op": "reload"})`.

При перезагрузке выполняются последовательные присваивания:

```python
self.graph = graph
self.query = Query(graph)
self._served_mtime = self._current_mtime()
self._currency_cache = None
```

Блокировка или единая неизменяемая версия состояния отсутствует.

В результате существует окно, в котором два поля ссылаются на разные поколения графа. При параллельных вызовах могут также перезаписываться служебные поля, предназначенные для текущего запроса.

Проблема особенно существенна для `source`, `impact`, `check`, `review` и операций, формирующих признаки неполноты ответа. Даже если конкретный MCP-транспорт сериализует пользовательские вызовы, фоновая перезагрузка уже создаёт независимый поток выполнения.

**Рекомендуемая архитектура:** неизменяемый объект `Snapshot`, включающий граф, `Query`, provenance, mtime и версию; атомарная публикация нового снимка; локальные переменные контекста каждого запроса вместо полей `Session`.

Тест должен одновременно выполнять сотни запросов и заменять граф двумя снимками с различающимися узлами. Приёмка — ни одного ответа со смешанными идентификаторами, счётчиками или метаданными разных снимков.

### F-06. `refresh` доверяет сохранённой команде из sidecar

**Приоритет: P2. Статус:** подтверждено чтением кода.

[`codemap/cli.py`, строки 891–905](https://github.com/kogriv/codemap/blob/def00ce1/codemap/cli.py#L891-L905):

```python
meta = read_meta(args.graph)
...
return main(meta["argv"])
```

`graph.json.meta.json` содержит ранее сохранённый список аргументов CLI и рабочий каталог. При `refresh` эти аргументы воспроизводятся.

В этой точке отсутствует проверка, что сохранённая команда действительно является `codemap build` и что она выполняет запись только в разрешённое место.

Это более узкая проблема, чем F-01: само по себе `main(meta["argv"])` не является произвольным выполнением команд ОС. Однако подменённый sidecar может заставить `refresh` выполнить **другую операцию Codemap**, включая операции с побочными эффектами.

Рекомендация — использовать отдельную типизированную схему рецепта сборки, проверять команду и пути, не допускать переключения на произвольные подкоманды, а при несовпадении идентификаторов графа и sidecar отказывать в автоматическом воспроизведении.

### F-07. Идентичность входного графа учитывает содержимое файлов, но не все параметры их интерпретации

**Приоритет: P2. Статус:** подтверждённая особенность алгоритма; влияние на реальный проект требует теста.

[`codemap/scope.py`, строки 137–190](https://github.com/kogriv/codemap/blob/def00ce1/codemap/scope.py#L137-L190) вычисляет `scope_id` по списку:

```python
f"{f['path']}\t{f['sha256']}"
```

При этом для каждого файла предварительно вычисляется `role`: `core`, `tests`, `docs` и другие корни.

Но в сам `scope_id` роль не включена.

Это означает, что одинаковый набор файлов с одинаковым содержимым получает один идентификатор независимо от различий в назначенных ролях. Между тем роль влияет на то, как Codemap строит и интерпретирует граф.

Следовательно, идентификатор подтверждает равенство **набора байтов и относительных путей**, но не полную эквивалентность **рецепта анализа**.

Нужен тест, в котором один и тот же набор файлов обрабатывается с различной принадлежностью к корням. Если итоговые графы различаются, но `scope_id` совпадает, обнаружится некорректная эквивалентность при проверке актуальности.

Исправление — включить в идентичность канонизированный профиль сборки: роли, типы корней, режим, влияющие на интерпретацию параметры и, при необходимости, версию алгоритма извлечения. Версию самого инструмента следует по-прежнему учитывать отдельно, чтобы не путать изменение кода проекта с обновлением анализатора.

Во время аудита появился коммит [`39c86a0`](https://github.com/kogriv/codemap/commit/39c86a0937cd9f86b7597d9120b9c141cfecc528) с версией **0.0.44**.

### F-08. Исправление известного цикла в 0.0.44 имеет слишком широкое условие

**Приоритет: P2. Статус:** подтверждённый логический контрпример; интеграционный тест не проводился.

Новая функция [`_absorbing()`](https://github.com/kogriv/codemap/blob/39c86a0/codemap/arch.py#L442-L446) определяет, что известная группа циклических модулей поглощена большей новой группой:

```python
return next(
    (m for m in now
     if len(m & group) >= 2 and not m <= group),
    None,
)
```

Однако пересечение минимум по двум вершинам **не доказывает поглощение исходной группы**.

Рассмотрим пример:

| Состояние | Модули |
|---|---|
| Известная ранее группа | `{a, b, c}` |
| Новая циклическая группа | `{a, b, d}` |
| Пересечение | `{a, b}` |

Исходная группа `{a, b, c}` не содержится в новой `{a, b, d}`. Модуль `c` отсутствует. Тем не менее проверка `len(m & group) >= 2` считает это поглощением.

Аналогичное условие используется в [`devkit/ratchet.py`](https://github.com/kogriv/codemap/blob/39c86a0/codemap/devkit/ratchet.py#L235-L243) для решения, следует ли удалять устаревшую группу при `--tighten`.

В результате возможно ошибочное сохранение устаревшего исключения из архитектурного контракта.

Корректный критерий именно *поглощения* должен проверять включение всей известной группы в новую:

```python
group <= m
```

Если первоначальная семантика группы допускает подмножества, их нужно классифицировать отдельно — нельзя одним условием смешивать «цикл сохранился», «группа расширилась» и «часть модулей осталась в другом цикле».

Нужно добавить минимум три теста: поглощение `{a,b}` группой `{a,b,c}`, частичное пересечение `{a,b,c}` с `{a,b,d}` и реальное исчезновение исходного цикла.

**Важно:** не утверждается, что весь архитектурный gate из-за этого обязательно пропустит новое нарушение: его оценка нарушений выполняется отдельно. Подтверждённая проблема относится к классификации известного цикла и управлению его baseline.

### Что реально улучшилось в 0.0.44

В [`extract/behavior.py`](https://github.com/kogriv/codemap/blob/39c86a0/codemap/extract/behavior.py#L1016-L1065) появилась обработка `import_module("pkg.sub." + name)` и последующего обращения к атрибуту. Добавляются рёбра `references` с `resolution="dispatch"`.

Это закрывает зарегистрированный сценарий, при котором живые функции плагинов попадали в список неиспользуемого публичного кода. При этом новые рёбра сознательно классифицируются как **heuristic**, а не exact.

Результат улучшает recall, но способен добавлять лишние зависимости: реализация ищет `import_module` и `getattr`/`hasattr` в одной области, не доказывая поток данных между возвращённым объектом модуля и аргументом `getattr`.

Например, динамический импорт одного семейства плагинов и независимый `getattr` другого объекта в той же функции потенциально будут объединены в предположение о достижимости.

Это допустимо для эвристического поиска кандидатов, но не для утверждений об обязательной зависимости.

Тесты для R1-C120 добавлены в [`tests/test_r1c120_dispatch_absorbed.py`](https://github.com/kogriv/codemap/blob/39c86a0/tests/test_r1c120_dispatch_absorbed.py). На первоначальном этапе проверки CI нового коммита ещё выполнялся; успешный CI предыдущего снимка 0.0.43 не доказывал результаты версии 0.0.44. Позднее были получены результаты, разобранные в F-12: исходный релизный коммит 0.0.44 не прошёл CI.

## 5. Дополнительные риски безопасности и надёжности

### F-09. Небезопасная подстановка проектных путей в генерируемые shell-скрипты

**Приоритет: P1 при работе с недоверенными проектами. Статус:** подтверждённый опасный шаблон.

[`codemap/devkit/templates/post-commit.sh`](https://github.com/kogriv/codemap/blob/39c86a0/codemap/devkit/templates/post-commit.sh) содержит:

```bash
nice -n 19 $C build {{package}} --deep --repeat 2 {{build_args}} ...
```

В шаблон подставляется `package` из состояния Devkit. В отличие от `build_args`, которое формируется через `shlex.join()`, здесь имя пакета не экранируется как отдельный shell-аргумент.

Похожая конструкция присутствует в [`github-workflow.yml`](https://github.com/kogriv/codemap/blob/39c86a0/codemap/devkit/templates/github-workflow.yml).

При наличии специальных символов shell в управляемом значении результат может интерпретироваться как часть команды, а не путь.

Даже если обычные имена Python-пакетов безопасны, сохранённая конфигурация Devkit является отдельным входом, который нельзя считать доверенным только потому, что он создан в прошлом.

**Исправление:** централизованное экранирование каждого shell-аргумента, проверка поддерживаемого формата путей, отдельные рендереры для Bash и YAML, негативные тесты со специальными символами и проверка сгенерированных файлов через shell-парсер.

### F-10. Неатомарная публикация основного графа

**Приоритет: P2. Статус:** подтверждено кодом.

[`codemap/store.py`](https://github.com/kogriv/codemap/blob/39c86a0/codemap/store.py) сохраняет граф напрямую через `Path.write_text()`.

Если процесс прервётся во время записи, файл может остаться пустым или частично записанным. При одновременном чтении другой процесс может получить некорректный JSON.

Механизм Devkit частично решает проблему через построение временного графа и последующее переименование, но прямой `codemap build -o graph.json` по-прежнему использует базовый `store.save()`.

**Рекомендуемое исправление:** сериализация в временный файл в том же каталоге, `flush`/`fsync` при необходимости гарантий сохранности и атомарный `os.replace()`. Метаданные графа следует связывать с идентификатором конкретного артефакта, поскольку согласованность двух отдельных файлов одним переименованием не обеспечивается.

### F-11. Неатомарное обновление каталога `advise`

**Приоритет: P3. Статус:** подтверждено кодом.

[`codemap/advise/refresh.py`](https://github.com/kogriv/codemap/blob/39c86a0/codemap/advise/refresh.py) сначала скачивает и валидирует оба файла, но затем записывает их последовательно:

```python
(cdir / "matrix.toml").write_bytes(mraw)
(cdir / "feed.json").write_bytes(fraw)
```

Между этими операциями каталог содержит файлы разных поколений. При сбое записи второго файла первое изменение уже выполнено.

Это нарушает заявленный транзакционный смысл операции: успешная предварительная проверка двух файлов ещё не гарантирует совместную публикацию.

Исправление — сохранять новую пару в каталог отдельной версии и атомарно переключать указатель на активную версию. При следующем запуске оставшийся незавершённый каталог можно безопасно удалить.

### F-12. Новый релиз 0.0.44 не проходит CI

**Приоритет: P1 для выпуска. Статус:** подтверждено GitHub Actions на релизном коммите `39c86a0`.

На коммите `39c86a0` получена следующая картина:

| Job | Результат |
|---|---|
| Тесты Python 3.11 | **Ошибка**, шаг `Run the suite` |
| Тесты Python 3.12 | **Ошибка**, шаг `Run the suite` |
| Тесты Python 3.13 | **Ошибка**, шаг `Run the suite` |
| Тесты Python 3.14 | **Ошибка**, шаг `Run the suite` |
| Детерминизм fast | Успех |
| Wheel и smoke-тест | Успех |
| SCIP / ctags | Успех |

[Результаты запуска GitHub Actions](https://github.com/kogriv/codemap/actions/runs/45113261096).

Во всех четырёх версиях Python сбой произошёл на шаге `Run the suite`. При этом сборка wheel, проверка детерминизма и интеграция с внешними инструментами завершились успешно.

На момент получения результатов **точную причину падения установить не удалось:** детальные журналы не были доступны через используемый способ чтения GitHub. Было бы некорректно приписывать сбой новой обработке диспетчеров или изменению числа тестов в README без доказательства.

Это достаточное основание **не считать исходный релизный коммит 0.0.44 проверенным релизом**. Предыдущий коммит `def00ce1` с версией 0.0.43 проходил CI на всех четырёх версиях Python.

До выяснения причины следовало сохранять 0.0.43 как последнюю из двух рассмотренных версий с подтверждённым зелёным CI, учитывая при этом известные функциональные ограничения 0.0.43, исправленные в исходниках 0.0.44.

**Уточнение по F-12 после дополнительной проверки.** Следующий коммит [`cd1e416`](https://github.com/kogriv/codemap/commit/cd1e416cd72ad5faf26ddfa69d9c3d721f167bf6) объясняет причину релизного падения. Согласно записи разработчика в `BACKLOG.md`, проверка самоизмерения R1-C13 требовала точности поиска определения через `grep` не ниже 0,4 **для каждого отдельного символа**. Новый символ `load` нарушил это условие, поскольку `def load` также встречается внутри тестовых строк-фикстур.

Тест изменён: теперь проверяются медиана не ниже 0,4 и средняя точность не ниже 0,5 по выборке. Это разумная корректировка чрезмерно жёсткого универсального утверждения, но она **не доказывает**, что сама метрика отражает реальную точность поиска определений на других репозиториях. Новый CI был запущен; его окончательный результат на момент заключительной сверки оставался неизвестным.

## 6. Проверка точности: что действительно доказывают исследования проекта

Это одна из наиболее важных частей аудита. Codemap содержит необычно подробные исследования собственных ограничений, в том числе отрицательные результаты.

### 6.1. Точность графа вызовов

Согласно [`docs/accuracy.md`](https://github.com/kogriv/codemap/blob/39c86a0/docs/accuracy.md), на ручном наборе из 12 сценариев:

| Метрика | Fast | Deep |
|---|---:|---:|
| Precision | 100% | 100% |
| Recall разрешимых вызовов | 100% | 100% |
| Recall всех истинных вызовов | 66,7% | 68,4% |
| Рёбра к несуществующим узлам | 0 | 0 |

**Данные диаграммы полноты графа вызовов:**

| Режим | Recall всех истинных вызовов |
|---|---:|
| Fast | 66,7% |
| Deep | 68,4% |

Это доля найденных истинных вызовов, включая динамические случаи, которые статический анализ не разрешает.

**Ключевая оговорка:** 100% precision на 12 заранее размеченных случаях — не доказательство 100% precision на произвольных Python-проектах.

Этот набор полезен как регрессионный тест конкретных механизмов, но статистически ограничен. Особенно это важно после появления в 0.0.44 эвристических рёбер `references:dispatch`, которые не относятся к тем же exact-вызовам.

В бенчмарке на реальном проекте `bquant` анализировались 6 323 места вызова в 833 функциях:

| Категория мест вызова | Доля |
|---|---:|
| Разрешённые внутренние вызовы | 25,3% |
| Разрешённые внешние вызовы | 46,1% |
| Неразрешённые вызовы | 28,6% |

**Данные диаграммы классификации 6 323 мест вызова в `bquant`:** это распределение call-sites, а не precision/recall.

25,3% — доля всех мест вызова, разрешённых во внутренние символы проекта. Это **не recall графа**: ещё 46,1% обращаются к внешним библиотекам, а среди 28,6% неразрешённых есть как внутренние, так и внешние вызовы.

Поэтому нельзя делать утверждение «Codemap обнаруживает 25% зависимостей». Но нельзя утверждать и противоположное — что граф практически полный.

**Оценка:** проект корректно признаёт неполноту, однако для применения в автоматическом рефакторинге требуется более широкий независимый benchmark с реальным runtime-эталоном.

### 6.2. Точность поиска тестов

[`docs/test-mapping.md`](https://github.com/kogriv/codemap/blob/39c86a0/docs/test-mapping.md) содержит сравнение с `coverage.py` на 484 тестах:

- Для 57% реально исполняемых символов deep-граф находит кандидатов в тесты в пределах трёх шагов; fast — для 43%.
- Медианная precision среди найденных ответов — 1,00.
- Медианный recall по действительно исполняющим символ тестам среди полученных ответов — 0,43.
- 16% символов, выполнение которых подтверждено coverage, возвращают `unknown` в пределах трёх шагов.

Это практически полезный инструмент **приоритизации тестов**, но не полноценная замена test selection по runtime coverage.

Особенно показательна потеря точности на больших расстояниях:

| Расстояние по графу | Медианная precision | Медианное число тестов |
|---|---:|---:|
| 1 переход | 1,00 | 2 |
| 2 перехода | 1,00 | 4 |
| 3 перехода | 1,00 | 8 |
| 4 перехода | 0,67 | 78 |
| 5 переходов | 0,33 | 78 |

Ограничение по умолчанию тремя переходами обосновано данными, а не выбрано произвольно.

При этом тесты, найденные через Protocol/registry fan-out, могут оказаться только потенциально достигающими код. Наличие пути по графу не гарантирует фактическое исполнение функции при запуске конкретного теста.

### 6.3. Dead-code analysis: высокая цена ложного положительного результата

[`docs/dead-code.md`](https://github.com/kogriv/codemap/blob/39c86a0/docs/dead-code.md) фиксирует показательный случай с Pillow.

До исправления обработки переопределённых методов 40 из 63 кандидатов с высокой уверенностью были реализациями `_open`, которые в действительности достижимы через вызов базового класса.

Это более 63% ошибочных кандидатов в самой опасной для пользователя категории — той, по которой могут удалять код.

После исправления количество high-кандидатов для Pillow сократилось до 15. Но этот пример демонстрирует общий принцип: алгоритм, построенный на отсутствии входящих рёбер, может выдавать ложные результаты из-за неучтённого способа диспетчеризации.

Версия 0.0.44 исправляет ещё один подобный случай с плагинами, загружаемыми по имени. Однако динамические регистрации, `entry_points`, DI-контейнеры, monkeypatching и некоторые рефлексивные конструкции по-прежнему требуют осторожности.

**Практический вывод:** `dead-code` пригоден для поиска кандидатов на расследование. Удалять функции автоматически по его результату нельзя.

### 6.4. Context pack: положительные и отрицательные результаты

Здесь особенно важно не смешивать разные поколения алгоритма.

В эксперименте [`research/pack_usefulness.md`](https://github.com/kogriv/codemap/blob/39c86a0/research/pack_usefulness.md) односторонний `pack`, проходящий от изменённого файла к используемым зависимостям, показал recall@10 всего 0,189 против 0,354 у `grep`. На выборке изменений тестов его recall@10 оказался равным нулю.

Позднее алгоритм был изменён: теперь seeded pack по умолчанию проходит граф в обе стороны — к зависимостям и к потребителям. В [`docs/pack.md`](https://github.com/kogriv/codemap/blob/39c86a0/docs/pack.md) приведены результаты двух репозиториев:

| Метод | Первый проект, recall@10 | Второй проект, recall@10 |
|---|---:|---:|
| Pack, только зависимости | 18,9% | 20,2% |
| Pack, обе стороны | **41,6%** | **59,9%** |
| Impact | 33,2% | 40,6% |
| Grep | 35,4% | 38,7% |

Новая версия действительно лучше предыдущей по данной метрике. Однако на первом проекте доверительный интервал превосходства над grep включает ноль. На втором превосходство убедительнее.

Кроме того, оценивается попадание в список файлов, изменённых в одном коммите. Это не равно успешности coding agent на реальной задаче.

С другой стороны, исследование [`RepoBench`](https://github.com/kogriv/codemap/blob/39c86a0/research/repobench_context.md) даёт отрицательный результат для ранжирования возможных дополнений кода: на этом benchmark графовый ранжировщик не превосходит надёжно простые базовые методы. На повторных употреблениях символов эвристика по недавности оказывается значительно сильнее.

**Вывод:** граф приносит пользу там, где нужна структура связей и охват изменений. Его преимущества в задачах выбора контекста и code completion зависят от конкретной постановки, и они не универсальны.

### 6.5. Инкрементальная сборка

По [`docs/incremental.md`](https://github.com/kogriv/codemap/blob/39c86a0/docs/incremental.md):

- Полная deep-сборка на измеренном проекте занимает около 60 секунд.
- Инкрементальный анализ изменения одного файла — около 5 секунд.
- Fast-инкрементальная сборка проверена на побайтовую эквивалентность полной.
- Deep-инкрементальная сборка **не гарантирует** эквивалентность полной из-за нестабильного разрешения отдельных рёбер Jedi.

Тонкая проблема заключается в закреплении пропуска: если при исходной deep-сборке не обнаружено реальное ребро, неизменённая часть графа может сохранять этот пропуск во всех последующих инкрементальных обновлениях.

В измерении пять повторных инкрементальных обновлений не восстановили исходно пропущенное ребро; пять полных повторных сборок обнаружили его.

Проект документирует это и предлагает `--repeat N`, но повторная выборка не гарантирует обнаружения всех динамических связей.

**Рекомендация:** для вопросов вида «кто вызывает?» допустим быстрый инкрементальный граф с оговорками. Для решений вида «можно ли удалить?», «этот код нигде не используется?» или «ничего не сломается?» следует требовать свежий полный анализ и дополнительную проверку.

## 7. Дополнительные замечания по архитектурным контрактам, форматам и supply chain

### F-13. Архитектурная проверка не запрещает неизвестную актуальность графа

**Приоритет: P2. Статус:** подтверждено кодом.

[`_check_exit()`](https://github.com/kogriv/codemap/blob/39c86a0/codemap/cli.py#L990-L998) возвращает ошибку при нарушениях контракта или при состоянии графа `behind`.

Но возможное состояние `unknown` не приводит к отказу:

```python
behind = currency is not None and currency.get("status") == "behind"
return 2 if (violations or (behind and not allow_stale)) else 0
```

Это сознательное различие между «известно устаревшим» и «невозможно проверить актуальность», но для строгого CI-gate неизвестность может быть столь же неприемлемой.

Проверка старого или импортированного графа без достаточного provenance способна завершиться кодом 0, хотя соответствие графа текущему дереву не подтверждено.

**Исправление:** добавить режим `--require-current-graph`, при котором допускаются только `current` и `built_now`. В сгенерированном CI Devkit желательно использовать именно этот режим, а не полагаться исключительно на отсутствие обнаруженного состояния `behind`.

Это не отменяет существующие сильные стороны `check`: он уже отказывает при неразбираемом TOML, неизвестных ключах контракта и отсутствующем контракте при `--require-contract`.

### F-14. Формат загружаемого графа не имеет строгой границы валидации

**Приоритет: P2. Статус:** подтверждено кодом.

[`Graph.from_dict()`](https://github.com/kogriv/codemap/blob/39c86a0/codemap/model.py#L392-L402) непосредственно создаёт объекты из загруженных JSON-структур.

Не видно обязательной проверки целостности всех инвариантов:

- допустимость идентификаторов и файловых путей;
- корректность диапазонов строк;
- допустимые типы рёбер и отношений;
- существование конечных узлов внутренних рёбер;
- ограничение размера графа;
- строгая совместимость схемы при обработке потенциально недоверенных артефактов.

Часть этих условий может диагностироваться позднее, а `loaded_schema` сохраняет объявленную версию формата. Но диагностика не равнозначна отказу при нарушении границы доверия.

Особенно важно, что загруженный граф участвует не только в вычислениях: он способен влиять на файловые операции `source` и `vault`.

**Исправление:** отдельный строгий валидатор графа на входе с режимами `trusted` и `untrusted`, ограничениями размера, проверкой структурных инвариантов и обязательной нормализацией путей перед файловыми операциями.

### F-15. Недостаточно жёсткая фиксация цепочки поставки и инструментов CI

**Приоритет: P2. Статус:** подтверждённый пробел в конфигурации.

[`pyproject.toml`](https://github.com/kogriv/codemap/blob/39c86a0/pyproject.toml) использует минимальные версии зависимостей без верхних ограничений:

```toml
"griffe>=2.0"
"networkx>=3.0"
"jedi>=0.19"
```

В [`CI`](https://github.com/kogriv/codemap/blob/39c86a0/.github/workflows/ci.yml) применяется установка без зафиксированного lock-файла, а GitHub Actions подключаются по major-тегам `actions/checkout@v4` и `actions/setup-python@v5`.

Бинарный архив SCIP скачивается и распаковывается без проверки заранее зафиксированного криптографического хэша.

Здесь важно различать два аспекта. Фиксация внешнего `bquant` на конкретном commit SHA и выбор определённой версии SCIP уже являются правильными мерами воспроизводимости. Однако фиксированная версия архива без проверки его содержимого и изменяемые версии остальных зависимостей не обеспечивают полной воспроизводимости и целостности цепочки поставки.

В дереве также не обнаружены отдельные workflow для security scanning, dependency auditing или проверки уязвимых зависимостей.

**Рекомендации:** отдельный фиксированный набор зависимостей для CI, SHA-pinning Actions, проверка хэша внешнего бинарника, `pip-audit`, SBOM, а для релизов — проверяемое происхождение артефактов и запрет публикации до успешного прохождения обязательного CI.

### F-16. Token budget в `pack` основан на приближении, а не на реальной токенизации

**Приоритет: P3. Статус:** подтверждено реализацией.

[`codemap/serve/pack.py`](https://github.com/kogriv/codemap/blob/39c86a0/codemap/serve/pack.py#L48-L50) оценивает расход токенов по длине текста:

```python
return max(1, len(text) // 4)
```

Это не эквивалентно токенизации GPT, Claude или других моделей. Для исходного кода, длинных идентификаторов, Unicode-текста и структурированных фрагментов погрешность может быть существенной.

Поэтому утверждение, что результат никогда не превышает budget, справедливо **только для внутренней оценочной метрики**, но не обязательно для фактических токенов модели.

**Исправление:** оставить лёгкий эвристический режим как default, но явно назвать его `estimated_tokens`, а для интеграции с агентами добавить необязательный точный tokenizer и небольшой резерв для оболочки MCP-запроса.

| Подсистема | Оценка | Основной технический риск |
|---|---|---|
| `model.py`, `store.py` | Хорошая каноническая модель | Недостаточная проверка загружаемых артефактов, неатомарная запись |
| `extract/griffe_extractor.py` | Богатая модель структуры Python | Граница видимости динамического и вложенного кода |

| `extract/roots.py` | Анализ дополнительных корней проекта | Сложность согласования core/consumer и путей |
| `query.py` | Единый графовый backend, разделённые индексы | Крупный модуль и стоимость некоторых алгоритмов |
| `arch.py` | Формальные архитектурные контракты | Семантика исключений и сложность ratchet |

| `serve/pack.py`, `rag.py` | Удобный слой для AI-агентов | Контекстная релевантность и приблизительные токены |
| `devkit/*` | Управляемые артефакты, контроль ручных изменений | Выполнение команд и работа с путями из конфигурации |
| `integrations/*` | Capability-first, opt-in | Доверие к внешним инструментам и их результатам |
| `advise/*` | Накопленная экспертиза по другим инструментам | Актуальность, целостность и атомарность внешнего каталога |

### 8.1. Монолитность крупных модулей

Наиболее крупные файлы:

| Файл | Размер |
|---|---:|
| `codemap/query.py` | 95 КБ |
| `codemap/cli.py` | 87 КБ |
| `codemap/extract/behavior.py` | 60 КБ |
| `codemap/extract/griffe_extractor.py` | 50 КБ |
| `codemap/serve/session.py` | 47 КБ |

Сам по себе размер файла не является дефектом. Но в данном случае сложность совпадает с критическими границами поведения: обработкой команд, разрешением вызовов, построением индексов, нормализацией ответов и хранением состояния.

В `Session` одновременно реализованы маршрутизация операций, управление состоянием, metadata envelope и часть доменной логики. В `query.py` сосредоточены разные категории графовых вычислений.

Это повышает риск того, что исправление одного сценария изменит результат другого — как произошло с универсальным тестовым утверждением о точности поиска `grep` после появления новых символов в версии 0.0.44.

**Рекомендуемый рефакторинг:** разделить неизменяемые индексы графа, алгоритмы запросов, протокол ответов и транспорт. Для извлечения вызовов отдельно выделить реестр маршрутов разрешения с их гарантиями (`exact`, `typed`, `heuristic`, `unresolved`).

### 8.2. Положительная сторона: модель неопределённости

У Codemap уже есть важные механизмы, которых часто не хватает аналогичным инструментам:

- `epistemic` — объяснение причин неполноты графа;
- `resolved` — неоднозначность разрешения символа;
- `limit` — сведения об ограничении выдачи;
- `currency` — состояние актуальности графа;
- `provenance` — история и режим его построения;
- `diagnostics` — проблемы и границы поддерживаемых выводов.

Это правильная архитектура для machine-consumable анализа.

Однако эти блоки должны рассматриваться как часть обязательного API-контракта, а не факультативные текстовые предупреждения. Каждая новая категория ребра должна получать формальное описание семантики, точности и влияния на операции `impact`, `dead-code`, `tests`, `check` и `pack`.

### 8.3. Архитектурные циклы реализованы лучше типичного подхода

[`query.py`](https://github.com/kogriv/codemap/blob/39c86a0/codemap/query.py#L1281-L1411) не пытается перечислять все простые циклы в больших графах как основной результат.

Вместо этого используются сильно связные компоненты (SCC, или *tangles*) и один репрезентативный цикл для объяснения.

Это принципиально правильное решение: число простых циклов может расти комбинаторно. Переход к SCC делает отчёты компактнее и устойчивее.

Дополнительно различаются:

- eager import cycles — возможные проблемы времени импорта;
- lazy import cycles — циклы зависимостей через локальные импорты;
- type-only cycles — зависимости, не исполняющиеся в runtime.

Такая классификация полезнее простого утверждения «обнаружено N циклов», потому что эти связи имеют разные последствия.

Проблема F-08 относится не к этому базовому алгоритму, а к надстроенной логике исключений из архитектурного контракта.

## 9. Производительность и масштабирование

### 9.1. Различать стоимость построения и стоимость запросов

Codemap использует архитектуру, при которой дорогой анализ исходников выполняется заранее, а большинство запросов обслуживается готовыми индексами.

Это оправданно: один граф может использоваться многократно для поиска символов, построения отчётов, анализа изменений и общения с агентом через MCP.

Но в текущем дизайне остаются несколько ограничений масштабирования.

| Операция | Основной фактор стоимости | Риск на большом проекте |
|---|---|---|
| Fast build | Разбор структуры всех входных файлов | Рост времени с объёмом исходников |
| Deep build | Jedi и разрешение типов/вызовов | Высокая стоимость отдельных модулей |
| Incremental deep | Перерасчёт затронутых модулей | Сохранение пропущенных связей |
| `scope`/watch | Повторное хэширование файлов | Постоянная нагрузка на диск и CPU |
| `Query` initialization | Построение индексов NetworkX | Пиковое потребление памяти |
| `pack`/`rank` | PageRank | CPU-нагрузка на каждом ранжировании |
| `source` | Чтение исходного файла | Лишний I/O и память |
| JSON export | Сериализация полного графа | Размер артефакта и временные копии |

### 9.2. Постоянное хэширование исходников

[`resolve_scope()`](https://github.com/kogriv/codemap/blob/39c86a0/codemap/scope.py#L137-L188) читает содержимое файлов и вычисляет SHA-256.

В документации приводится измерение примерно 50 мс для проекта из 292 файлов объёмом 4,7 МБ. Для такого масштаба подход приемлем.

Однако при росте дерева до десятков или сотен тысяч файлов постоянное повторное чтение всего содержимого становится дорогим. Особенно при работе на сетевых дисках или в монорепозитории.

Здесь не следует заменять content hash только на mtime: это ухудшит надёжность определения актуальности. Лучше использовать многоуровневую схему: файловые события для быстрого обнаружения изменений, кэш размеров/mtime для отбора кандидатов и периодическую полную проверку содержимого.

Также полезны лимиты на стоимость одного цикла watch и метрики времени хэширования.

### 9.3. Повторный PageRank

[`Query.rank()`](https://github.com/kogriv/codemap/blob/39c86a0/codemap/query.py#L1226-L1257) строит ориентированный граф для ранжирования и запускает собственную реализацию PageRank.

Она корректно использует детерминированный порядок обработки узлов, но исполняется на Python и повторяет итерации при запросе ранга.

Кэширования результатов по `graph snapshot + seeds + direction + edge types` на рассмотренном пути не обнаружено.

Для небольшого графа это несущественно. Для резидентного MCP-сервера, которому агент часто задаёт похожие вопросы, появляется возможность существенно сократить работу.

**Рекомендация:** кэшировать ранги глобального режима, ограниченно кэшировать распространённые seeded-запросы и инвалидировать кэш атомарно при смене снимка графа. Перед оптимизацией измерить hit rate и реальную задержку.

### 9.4. Необходим отдельный benchmark масштабируемости

В репозитории присутствуют измерения на реальных проектах, но они не заменяют систематическую характеристику пределов продукта.

Нужен воспроизводимый набор как минимум из трёх классов проектов: небольшой Python-пакет, крупный библиотечный проект и монорепозиторий с несколькими consumer roots.

Для каждого следует фиксировать время полной fast/deep-сборки, incremental P50/P95, RSS, размер JSON, время загрузки графа, P50/P95 запросов MCP, стоимость watch в простое и поведение при смене снапшота.

Пока таких сопоставимых данных нет, утверждать производственную масштабируемость Codemap на произвольные монорепозитории нельзя.

## 10. Тестирование, CI/CD и качество разработки

### 10.1. Что реализовано хорошо

Тестовая инфраструктура производит значительно более сильное впечатление, чем типичная инфраструктура небольшого open-source анализатора.

В частности:

- Проверяется совместимость Python 3.11–3.14.
- Есть тесты на настоящем стороннем коде `bquant`, зафиксированном по коммиту.
- Проверяется установка собранного wheel вне исходного дерева.
- Отдельно проверяется побайтовая детерминированность fast-режима.
- SCIP и ctags тестируются против настоящих внешних CLI.
- Пропуск обязательных dogfood-тестов не превращается в незаметный успешный запуск.
- Используются негативные и регрессионные сценарии, возникшие после конкретных ошибок.
- Для части изменений проверяется, что мутация реализации действительно ломает нужный тест.

Это реальные признаки зрелой инженерной практики.

### 10.2. Главный недостаток тестового процесса

**Большое число тестов не означает равномерный охват рисков.**

Существующие 1421 собранных тест-кейсов в состоянии 0.0.44 хорошо подтверждают многие функциональные контрактные сценарии. Но это не является доказательством, что достаточно проверены:

1. Недоверенные конфигурации Devkit и графы.
2. Файловые операции с символьными ссылками и выходом за корень.
3. Конкурентная работа Session и reload.
4. Корректность входного протокола при произвольных JSON-значениях.
5. Целостность результатов после сбоя между несколькими файловыми записями.
6. Большие графы с предельно высокой связностью.
7. Обобщаемость точности call graph на независимые проекты.

Это отдельные классы тестов, не заменяемые расширением существующего набора обычных unit tests.

Причина падения 0.0.44 оказалась связана с излишне сильным тестовым утверждением, а не с подтверждённой неработоспособностью продукта.

Тем не менее правильная практика — **релиз формируется из уже прошедшего обязательные проверки коммита**, а не подтверждается последующим исправлением после красного CI.

Желательно также разделить показатели качества алгоритма и инварианты продукта. Измерение точности по выборке не должно автоматически превращаться в универсальное утверждение для каждого нового символа.

## 11. Что я рекомендую исправить в первую очередь

Здесь важен порядок работ, а не количество закрытых пунктов backlog.

### Этап 1. Закрыть границы доверия

Наибольший риск проекта сейчас не в алгоритме анализа Python, а в инфраструктуре, которая обслуживает граф.

**Первым набором изменений** следует закрыть F-01, F-02, F-03 и F-09.

В первую очередь убрать запуск исполняемых файлов, восстановленных из потенциально недоверенной `.mcp.json`, при обычной проверке состояния Devkit.

Следом — внедрить единый механизм безопасного разрешения путей и использовать его для Devkit, source, vault и других файловых операций.

Затем изолировать shell-шаблоны от произвольных строк проектной конфигурации.

Приёмка должна включать негативные тесты, создающие заведомо опасные конфигурации во временном каталоге. Достаточно безвредных тестовых команд-маркеров и проверки, что они не исполняются.

### Этап 2. Стабилизировать протокол и состояние MCP

Исправить F-04 и F-05.

Модель `Session.handle()` должна гарантировать, что вся обработка некорректного запроса завершится структурированной ошибкой, а не исключением наружу.

Состояние графа необходимо публиковать как неизменяемый snapshot. Служебный контекст ответа — хранить отдельно для каждого запроса.

В результате исчезнет целый класс потенциальных race conditions, а не только конкретная гонка при reload.

### Этап 3. Укрепить инварианты графа и контрактов

Исправить F-06, F-07, F-08, F-13 и F-14.

Здесь центральная задача — связать три понятия:

- **Что анализировалось:** полный профиль входов, включая их роли.
- **Чем анализировалось:** версия и параметры анализатора.
- **Насколько результат применим:** актуальность, полнота, confidence и ограничения конкретной операции.

Именно такое разделение позволит надёжно использовать граф в автоматических проверках и агентных workflows.

### Этап 4. Улучшить устойчивость хранения

Исправить F-10 и F-11, обеспечить атомарную публикацию графа и каталога `advise`, тестировать аварийное завершение во всех точках между подготовкой и фиксацией нового состояния.

### Этап 5. Расширить измерения и производительность

После устранения рисков безопасности стоит заняться качеством рекомендаций и масштабируемостью.

Приоритет здесь — независимые accuracy-бенчмарки, реальная оценка пользы для coding agents, раздельные метрики exact/heuristic, нагрузки на MCP и производительность крупных графов.

Не рекомендую на этом этапе тратить ресурсы на новые виды отчётов, не подтвердив полезность и корректность уже существующих.

## 12. Итоговая оценка проекта

| Направление | Вывод |
|---|---|
| Архитектура | Сильная концепция с правильным разделением extraction, graph и query |
| Функциональность | Широкое покрытие задач анализа Python-кодовой базы |
| Корректность выводов | Хорошая система оговорок, но обнаружены существенные логические риски |
| Работа с динамическим Python | Постепенно улучшается; объективно неполная |
| Безопасность | Требует серьёзной доработки границ доверия |
| MCP-интеграция | Полезная и уже развитая, но нуждается в изоляции состояния |
| Тестирование | Сильное функциональное тестирование, недостаточное security/concurrency testing |
| Воспроизводимость | Лучше среднего; есть проблемы с зависимостями и релизным процессом |
| Производительность | Обоснованные локальные оптимизации; пределы на больших проектах не измерены |
| Документация | Очень подробная, содержит первичные измерения и отрицательные результаты |
| Готовность для AI coding agents | Хорошая для навигации, ограниченная для автономных решений об изменении/удалении кода |

### Где Codemap уже полезен

Проект можно обоснованно использовать для исследования собственных Python-репозиториев, навигации по определениям и вызовам, поиска потенциальных последствий изменений, построения архитектурных карт и генерации структурированного контекста для агента.

Сильнейший практический сценарий — **ускорение понимания кодовой базы**. Здесь предварительно построенный граф действительно даёт информацию, которую трудно быстро получить одиночным поиском по тексту.

### Где необходима осторожность

Я не рекомендую без дополнительных ограничений использовать Codemap:

- как привилегированный агентный инструмент в произвольном клонированном репозитории;
- как единственное основание для удаления «мёртвого» кода;
- как единственный источник правды при сложном динамическом dispatch;
- как доказательство отсутствия транзитивных зависимостей;
- как строгий release/architecture gate при неизвестной актуальности графа;
- как полностью воспроизводимый анализ без фиксации версии инструмента и зависимостей.

Эти ограничения имеют разную природу. Часть относится к неизбежной неполноте статического анализа Python, а часть — к вполне исправимым ошибкам реализации и процесса разработки.

### Окончательный вывод

**Codemap — инженерно содержательный проект с сильной архитектурной идеей, развитым набором функций и редкой для небольших open-source проектов дисциплиной измерения собственных результатов.**

Особенно положительно оцениваются архитектурные контракты, дифференциация eager/lazy/type-only циклов, provenance, честная маркировка неполноты графа и исследования, в которых автор не скрывает отрицательные результаты.

Но глубокая проверка показывает, что инженерная зрелость **аналитического ядра** пока выше, чем зрелость **границ доверия и эксплуатационной инфраструктуры**.

В коде обнаружены реальные пути выполнения команд из проектной конфигурации, неконтролируемые файловые операции, недостаточно защищённый входной протокол и разделяемое изменяемое состояние MCP-сервера. В новом релизе выявлено также чрезмерно широкое условие определения поглощённого цикла. Это не косметические замечания: они могут влиять на безопасность и достоверность решений, принимаемых по результатам Codemap.

Наиболее рациональная дальнейшая стратегия — не расширять функциональный охват любой ценой, а **сделать существующие 32 операции устойчивыми к недоверенным входам, согласованными по семантике и проверяемыми на независимых сценариях**.

Тогда проект сможет перейти из категории перспективного инструмента для опытного разработчика в категорию надёжного компонента инфраструктуры AI-assisted development.

**Граница выполненного аудита:** это углублённый статический аудит исходников, тестов, документации, коммитов и результатов CI, включая анализ перехода 0.0.43 → 0.0.44. Он не является завершённым динамическим security audit: локальный прогон кода, fuzzing, инструментальная проверка эксплуатационных сценариев и нагрузочные тесты остались невыполненными. Выводы, которые требуют таких проверок, выше явно отделены от подтверждённых анализом исходников.
