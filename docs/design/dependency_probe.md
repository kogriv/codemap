# Design — зависимость, которая отвечает неверно, — не то же, что отсутствующая

**Статус:** ✅ **сделано** (2026-10-14; схема графа и `ANSWER_FORMAT` существующих ответов не меняются;
сьют 1012 → 1022). **Мотивирует:** R1-C64, разбор R2.2 `jevgrep`, карточка
[`../../research/tools/jevgrep.md`](../../research/tools/jevgrep.md) §S2 (`jg doctor`). **Бэклог:** R1-C64.
**Пользовательские доки:** [`../accuracy.md`](../accuracy.md), [`../ci.md`](../ci.md).

**Неизменные инварианты:** source-only, детерминизм, два тира, resolved-or-honestly-flagged, закрытый
словарь рёбер, `extras` открытый, ответ называет, чего он не судил.

---

## 1. Что показывает чтение кода

Две зависимости делают работу, которую codemap не перепроверяет: **griffe** (структура: узлы,
`contains`, `export` через разрешение алиасов) и **jedi** (deep-тир: тип локальной переменной →
цель вызова). Проверено:

- обе — жёсткие зависимости в `pyproject.toml`; «проверка» сводится к тому, что `import` не упал;
- **версии их в артефакте нет**: `provenance.tool` — это только codemap (`name/version/commit/dirty`).
  Формулировка бэклога «объявляем версии в provenance» — **неверна**, замерено по коду
  (`codemap/provenance.py: tool_identity`); исправляется здесь, а не тихо;
- ответ jedi читается через `except Exception: return "", "unresolved"` (`extract/behavior.py:
  _resolve_jedi`), то есть jedi, который после обновления перестал резолвить, **не ломает сборку** — он
  превращает каждый deep-вызов в `unresolved`, и граф выходит просто беднее. Ровно класс R1-C13
  (партиальность от незапущенного резолвера), только причина снаружи нашего кода.

Замерено до правки: `jedi.Script`, подменённый заглушкой, которая на `goto`/`infer` отвечает пустотой, —
`codemap build --deep` на фикстуре выходит с кодом **0**, без единого предупреждения; из графа исчезают
три deep-ребра из четырёх (тот же замер стоит в R1-C59 как сторож просадки).

## 2. D1 — зонд: один факт с известным ответом на зависимость

**Решение: крошечный пакет, записываемый во временный каталог, и по одному факту на зависимость,
который codemap обязан из него извлечь.**

```python
# codemap_probe/__init__.py
from codemap_probe.core import helper as public_helper
# codemap_probe/core.py
class Engine:
    def run(self): ...
def helper(): ...
# codemap_probe/app.py
from codemap_probe import public_helper as ph
from codemap_probe.core import Engine
def main():
    engine = Engine()
    engine.run()
    return ph()
```

| зависимость | факт | почему только она |
|---|---|---|
| griffe | ребро `export codemap_probe → codemap_probe.core.helper` | цель ре-экспорта берётся из `Alias.target_path` griffe; иначе это ребро не порождает ничто |
| jedi | ребро `calls codemap_probe.app.main → codemap_probe.core.Engine.run`, `resolution="deep"` | тип `engine` выводится из присваивания; быстрый тир это ребро **не** строит (проверяется сторожем — иначе зонд проходил бы без jedi) |

Зонд идёт **через настоящий конвейер** (`extract`), а не через прямой вызов `jedi.Script`: проверяется
то, чем codemap пользуется, включая глотающий `except`. Прямой вызов jedi прошёл бы там, где наш
конвейер его ответ выбрасывает.

**Не бенчмарк.** Один факт на зависимость, держится или нет. Бэклог прямо: бенчмарк точности станет
шумным, и его отключат.

## 3. D2 — четыре исхода, а не «работает/не работает»

`ok` · `wrong` (импортируется, отвечает, ответ неверен — главный случай) · `absent` (не импортируется) ·
`error` (зонд упал с исключением). Плюс `not-run` для jedi, когда быстрый проход уже упал: deep-зонд
стоит на структуре griffe, и его результат тогда ничего не значит — это *unknown*, не *wrong*.

Различать `wrong` и `absent` — весь смысл пункта: отсутствующая зависимость ломает сборку громко,
неверно отвечающая — тихо.

## 4. D3 — где это видно: новая команда, а не новое поле

**Решение: `codemap doctor` (текст, `--json`), код выхода 0 — все зонды `ok`, 1 — иначе. И тот же зонд —
тест в сьюте.**

- **Тест в сьюте** — то, что ловит это у нас: CI ставит пакет без лок-файла (`pip install -e`,
  `.github/workflows/ci.yml`), то есть каждый прогон разрешает самые новые griffe/jedi, которые
  допускает `pyproject.toml`, — новая версия попадает под зонд на первом же push после её выхода.
- **`doctor`** — то, что пользователь может запустить у себя: окружение пользователя — не наше.
- **Почему не в `stats` и не в `provenance`.** Поле в ответе `stats` — новый блок, подъём
  `ANSWER_FORMAT`; версии зависимостей в `provenance` — подъём схемы. Новая команда не меняет ни одного
  существующего ответа; её собственный формат начинается под `ANSWER_FORMAT` 1.
- **Почему не в каждой `build --deep`.** Зонд стоит ~секунды (deep-сборка фикстуры), а deep-сборка
  реального дерева — минуты; это было бы дёшево. Но сборка, которая падает или предупреждает из-за
  временного каталога, — новый источник ложных тревог в чужих пайплайнах. Оставлено владельцу (§5).

## 5. Чего это не покрывает

- **Частичная деградация.** Зонд — один факт. jedi, который резолвит этот случай и перестал резолвить
  другой (`getattr`, дескрипторы, обобщения), зонд пропустит. Это цена «не бенчмарка», выбранная
  сознательно.
- **Сборка не проверяет себя.** `build --deep` с испорченной jedi по-прежнему выходит 0. Сказать об этом
  может `doctor`, тест в сьюте или — по факту — R1-C59 (просадка полноты против предыдущего графа того же
  дерева), но не сама сборка.
- **Версии в артефакте.** Граф не записывает версии griffe/jedi; `doctor` их печатает, граф — нет.
- **Прочие зависимости** (`mcp`, `scip`-extras, внешние адаптеры) не зондируются: они не участвуют в
  построении графа.
- **Не резолвер зонда.** Если codemap сам перестанет строить эти рёбра (наша регрессия, а не их), зонд
  тоже покраснеет и назовёт зависимость. Различить «их» и «наше» он не может; первым вопросом в отчёте
  будет версия зависимости — поэтому она печатается.

## 6. Пред-регистрация (до приёмочного прогона)

**Должно измениться:**

- **E1.** `codemap doctor` в чистом окружении worktree — две строки `ok` (griffe, jedi) с версиями,
  код выхода **0**.
- **E2.** `jedi.Script` подменён заглушкой, отвечающей пустотой, — `doctor`: jedi **`wrong`** с
  названным ожидаемым ребром; griffe `ok`; код выхода **1**.
- **E3.** `import jedi` невозможен — `doctor`: jedi **`absent`** (другое слово, чем в E2); код выхода **1**.
- **E4.** `griffe.Alias.target_path` подменён на неверный — `doctor`: griffe **`wrong`**; код выхода **1**.

**Должно остаться прежним:**

- **E5.** Подмена из E2, но `codemap build --deep` на той же фикстуре — код выхода **0**, ни одного
  `[warning]` (обычный прогон подмену не замечает — это и есть дефект, и правка его не трогает).
- **E6.** Пин `RENDERED_SHA` (R1-C63) не двигается; `stats` и остальные ответы — без изменений.
- **E7.** Быстрый тир на фикстуре зонда **не** строит jedi-ребро (иначе jedi-зонд проходил бы без jedi).

**Где отказ обязан прозвучать:** E2, E3, E4 — код 1 и слово исхода. **Если ничего не сделано**, E1–E4
краснеют: команды нет.

## 7. Сверка (после прогона, 2026-10-14)

Окружение worktree: griffe 2.3.2, jedi 0.20.1. Подмены — скриптом-обёрткой вокруг `codemap.cli.main`
(тот же код, что в тестах).

| # | ожидание | итог |
|---|---|---|
| **E1** | `doctor` в чистом окружении | ✅ `griffe 2.3.2 OK`, `jedi 0.20.1 OK`, `✅ every probe answered as expected.`, код **0**; ~0.7 с |
| **E2** | jedi отвечает пустотой | ✅ jedi **`WRONG`**, «expected edge `calls codemap_probe.app.main → codemap_probe.core.Engine.run (deep)` is not in the graph»; griffe `OK`; код **1** |
| **E3** | `import jedi` невозможен | ✅ jedi **`ABSENT`**, `not importable (ModuleNotFoundError: …)`; griffe `OK`; код **1** |
| **E4** | griffe разрешает алиасы неверно (`target_path` подменён) | ✅ griffe **`WRONG`**; jedi `OK` — неверная зависимость не приписана соседней; код **1** |
| **E5** | обычная сборка подмену не замечает | ✅ `build --deep` фикстуры с немой jedi: код **0**, `[warning]` — 0; граф объявляет `tier: deep`, а все `calls` в нём `imported` (`Engine.run` отсутствует) |
| **E6** | пин R1-C63 и прочие ответы | ✅ пин не двинулся (сьют зелёный) |
| **E7** | быстрый тир не строит jedi-ребро | ✅ нет ребра `→ Engine.run` в быстрой сборке зонда |

**Сюрпризы.**

- **Тот же дефект в масштабе живого дерева уже замерен в R1-C59 (E2 там):** с немой jedi deep-сборка
  `bquant@cb89a24` дала `calls 899`, `accesses 1621` — побайтно числа быстрого тира — и объявила
  `tier: deep`. То есть R1-C59 — второй, независимый сторож этого же класса: он заметит падение против
  предыдущего графа того же дерева, даже если `doctor` никто не запустит.
- **При `ABSENT` версия всё равно печатается** (`jedi 0.20.1 ABSENT`): метаданные дистрибутива на месте,
  импорт — нет. Это честно (так и есть), но читается неожиданно; оставлено.

**Сторожа:** `tests/test_r1c64_dependency_probe.py`, 10 тестов. Мутационно, каждая откатывалась:
`holds` всегда истина — краснеют 5; импорт не проверяется — 1 (`absent` превращается в `error`);
нет ветки `not-run` — 1; `doctor` всегда выходит 0 — 2; проверка `resolution="deep"` выкинута — 1
(тест, показывающий зонду то же ребро с маршрутом `imported`). Стабильно под `PYTHONHASHSEED`
0/1/7/42/99.

**Чего не проверено:** настоящая старая или будущая версия jedi/griffe (подмены — заглушки, не релизы);
Windows и пути с пробелами для временного каталога зонда; вызов `doctor` из установленного колеса
(job `wheel` его не запускает).
